# LUCID Agent IDE: plan of action and milestones (product gaps)

This is LUCID's own list of known weaknesses against NIST SP 800-171 Rev 3, for an assessor who has to decide how much of each requirement the product covers. Each item was checked against the source before it was listed; the "Verified in" column names the file that shows it. The customer's own POA&M (03.12.02) records how the organization compensates; the mitigations here are the ones available today.

Risk is the residual risk to CUI confidentiality on a typical deployment: High (CUI can be exposed without another failure), Moderate (needs a second failure or an insider), Low (assessment finding with little exposure).

| ID | Requirement | Weakness | Verified in | Risk | Mitigation available now | Target increment |
| --- | --- | --- | --- | --- | --- | --- |
| P-1 | 03.13.08, 03.13.11 | Outbound TLS to model providers and the AskSage gateway is performed by Bun / omp (BoringSSL), which is not a FIPS 140-validated module. P-FIPS.1 covers at-rest crypto only. | Contract A (`bun-boringssl` fallback, `fips:false`); `evidence.json` check 03.13.11 reports the module in use. | High for CMMC Level 2 (3.13.11 is a scored requirement); Moderate for confidentiality, since the cipher suites are standard TLS 1.2/1.3. | Send all egress through a FIPS-validated tunnel (FIPS-mode IPsec VPN or a FIPS-validated TLS-terminating proxy; agent children already honor `HTTP(S)_PROXY` via `harness/runs/sandbox_exec.ts` proxyChildEnv). Enable CUI lockdown so CUI goes only to the AskSage gateway or an attested enclave. | A follow-up to P-FIPS.1 (ADR-0473) that moves provider TLS onto the OS stack or a bundled FIPS provider. Not yet scheduled. |
| P-2 | 03.01.10 | No in-app session lock or idle timeout. | No idle lock in `desktop/main.ts` (powerMonitor is used only for shutdown) or `desktop/renderer/app.ts`. | Moderate | OS screen lock after inactivity, enforced by GPO / MDM; LUCID is unreadable while the OS session is locked. | Not scheduled; the OS lock is the intended control. |
| P-3 | 03.05.03 | No in-app MFA. LUCID trusts the OS session; remote guests use Firebase sign-in (`desktop/collab/relay_auth.ts`) whose MFA is the provider's. | No MFA / TOTP code in `desktop/` or `harness/`. | Moderate | MFA at OS sign-in (Windows Hello for Business, smart card) and at the IdP used for provider OAuth. | Not scheduled; MFA belongs to the OS / IdP. |
| P-4 | 03.17.03, 03.14.01 | macOS builds are not code-signed or notarized in public builds, so Gatekeeper cannot verify them and in-app update is inert on macOS. | `desktop/package.json` `mac.identity: null`; `.github/workflows/build-desktop.yml` header; `desktop/SIGNING.md`. | Moderate | Install from the release page and compare the published SHA-256; prefer Windows (Authenticode-signed, `desktop/build/win-signing.cjs`) for CUI work; MDM-managed installs. | P-RELEASE.2a (Apple Developer ID signing + notarization). |
| P-5 | 03.13.08, 03.05.12 | OAuth tokens for model providers stay in omp's `~/.omp/agent/agent.db` (table `auth_credentials`, column `data`); LUCID applies no encryption to them. [INFERENCE: omp stores the token blob unencrypted; LUCID's own reader treats `data` as the token blob.] | `desktop/auth_vault.ts` (DELETE / select of `data`); DECISIONS.md ADR-0472 Out of scope. | Moderate (user-profile file; readable by any process of that user) | Full-disk encryption; use API keys (sealed in the OS vault by `desktop/engine_vault.ts`) instead of OAuth logins for CUI work; disconnect unused OAuth logins in Settings. | P-VAULT-KEYS.2 (ADR-0480): OAuth credentials through omp's auth broker backed by the vault. |
| P-6 | 03.13.11, 03.05.07 | Paired-controller tokens are stored as argon2id hashes (`Bun.password`). argon2id is not a FIPS-approved algorithm. | `desktop/controller/store.ts` (pair(): `Bun.password.hash(token, { algorithm: "argon2id" })`). | Low (the token is 256 random bits; the hash only protects the at-rest copy) | Pair controllers only when needed and revoke unused pairings; the store file is written 0600. | Replace with HMAC-SHA256 under a vault-held key or PBKDF2-HMAC-SHA256 (approved, and sufficient for a 256-bit random token); fold into P-FIPS.1 follow-up. |
| P-7 | 03.04.10, 03.17.03 | No release-time SBOM before this increment: `harness/maintainer/sbom.ts` builds a manifest-level CycloneDX 1.5 SBOM (declared dependencies only, no transitive tree) and runs only from a demo script. | `harness/maintainer/sbom.ts` header; `harness/scripts/demo_maintainer.ts`; no SBOM step in `.github/workflows/build-desktop.yml`. | Low | `.github/workflows/compliance-evidence.yml` (this increment) generates a lockfile-based CycloneDX SBOM with cdxgen 12.9.0 on every `v*` tag. | P-COMPLY.1 adds the workflow; closes when the first tagged release has `sbom.cdx.json` and it is attached to the GitHub Release (the workflow uploads it as a run artifact only). |
| P-8 | 03.11.02, 03.05.12 | No secrets scanning in CI on pull requests. | None of the existing workflows runs gitleaks or another secret scanner (`.github/workflows/*.yml`). | Moderate | `compliance-evidence.yml` runs gitleaks 8.30.1 with `--redact` over the full history on every release tag and on demand; GitHub secret scanning if the repository plan provides it. | Add a PR-time gitleaks job (follow-up to P-COMPLY.1). |
| P-9 | 03.11.02, 03.17.03 | No dependency-review gate on pull requests; Dependabot proposes updates but nothing blocks a vulnerable addition. | No `actions/dependency-review-action` in `.github/workflows/`; `.github/dependabot.yml` present. | Moderate | osv-scanner 2.7.0 over all lockfiles on every release tag (`compliance-evidence.yml`); weekly CodeQL (`codeql.yml`). | Add a dependency-review or osv-scanner PR gate. Not yet scheduled. |
| P-10 | 03.03.08, 03.03.03 | The local audit file has default permissions, no rotation, no retention policy and no hash chaining; the user can delete it. SIEM connectors are in the private add-on. | `desktop/audit_export.ts` FileSink (`appendFileSync`, no chmod, no rotation). | Moderate | Collect `~/.omp/lucid-audit.jsonl` with the organization's log forwarder or the Enterprise SIEM connector (managed `logging.sink`), and keep the copy off-host. | Not yet scheduled. |
| P-11 | 03.13.06 | The personal default egress posture is allow-all; deny-by-default needs the user to turn allow-all off or a managed policy to hold it off. | `desktop/network_whitelist.ts` `DEFAULT_POSTURE = { allowAll: true, ... }`; `desktop/egress_policy.ts` clampPosture. | Moderate | Managed `security.egress.disableDangerMode: true` or `allowedHosts` (clamps allow-all off and locks it); CUI lockdown blocks public egress in CUI sessions. | Customer configuration; documented in README reference configuration. |
| P-12 | 03.17.03 | Third-party GitHub Actions are pinned by major version tag, not by commit SHA. | `uses:` lines in `.github/workflows/*.yml` (e.g. `actions/checkout@v7`). | Low | Repository branch protection; Dependabot `github-actions` updates (`.github/dependabot.yml`). | Pin actions by SHA. Not yet scheduled. |

Items closed by in-flight increments are tracked in their ADRs: P-FIPS.1 (ADR-0473) FIPS-validated at-rest crypto, P-VAULT-V2.1 (ADR-0474) unified vault, P-VAULT-UI.1 (ADR-0475) encrypted vault backup (03.08.09).
