## ADR-0479 -- P-COMPLY.1: NIST SP 800-171 Rev 3 evidence package (control matrix, POA&M, evidence CLI and route, release evidence workflow) (2026-11-03)

**Status:** Accepted -- BUILT in source and tests. Proof: `bun test desktop/compliance_report.test.ts` and `make compliance-evidence`.

**Context.** Defense customers must show their assessor (CMMC Level 2, DIBCAC) how a LUCID workstation meets NIST SP 800-171. The user chose Rev 3 as the primary baseline with a Rev 2 cross-reference, because DoD and CMMC still assess Rev 2. Until now the repo had the controls (CUI lockdown, managed policy, sandbox, approvals, OCSF audit, OS vault) but no assessor-facing map, no gap list, and no way to collect host evidence. `harness/brief/compliance.ts` (P-REPORT.6) is a keyword crosswalk of the change log, not a requirement-by-requirement matrix, and is left as is.

**Decision.**
1. `docs/compliance/control-matrix-r3.csv` is the single source of the matrix: all 130 Rev 3 identifiers (97 requirements, 33 withdrawn) in 17 families, columns r3 id, title, family, Rev 2 ids, withdrawal note, responsibility (LUCID / shared / customer / n-a), LUCID implementation with repo paths, how to verify, evidence artifact, status (implemented / partial / planned / gap / customer, or withdrawn). Ids, titles and withdrawals come from NIST SP 800-171r3 (https://doi.org/10.6028/NIST.SP.800-171r3), titles cross-checked against the NIST OSCAL catalog (usnistgov/oscal-content `NIST_SP800-171_rev3_catalog.json`); the Rev 2 mapping comes from NIST's change analysis (`sp800-171r2-to-r3-analysis.xlsx`). Rev 2 column = the Rev 2 id on the same row plus every Rev 2 id whose Rev 3 slot is withdrawn into this requirement. The one disagreement between the NIST sources (03.01.13: PDF "Addressed by 03.13.08", xlsx "Incorporated into 03.01.12") is marked `[verify]`.
2. `control-matrix-r3.md` is rendered from the CSV by `tools/compliance/matrix.ts` (`make compliance-matrix`); a test fails when the committed Markdown differs from the rendering.
3. `desktop/compliance_report.ts` produces Contract D's `ComplianceReport`: read-only probes (`gatherProbes`) and pure status logic (`buildReport`, one exported function per check). Probes never call `settings_store.load()` (it can migrate keys), never create a vault key, and never copy a secret value; the vault is read for its entry count only. OS probes (`reg`, `manage-bde`, Shell BitLocker property, `fdesetup`, `lsblk`, `Get-AuthenticodeSignature`, `codesign`) run asynchronously with a 20 s timeout and degrade to `unknown` with the reason, so the HTTP route never blocks the engine.
4. Contracts A and B are read in one adapter, `platformProbes()`. This branch has neither `harness/crypto/fips_crypto.ts` nor the zero-argument `vaultStatus()`, so the adapter loads `cryptoInfo()` dynamically when the module exists and otherwise reports Bun BoringSSL with `fips:false`, and reads the vault through the P-VAULT-KEYS.1 API (`vaultStatus(dir)`, `readVault(dir)`). `CryptoProviderInfo` is mirrored locally. **Integration dependency:** the parent replaces the dynamic import with a static `import { cryptoInfo }`, imports the type from fips_crypto.ts, and switches the vault read to Contract B `vaultStatus()` (custody, state, entries).
5. Surfaces: `bun run tools/compliance/evidence.ts [--out <dir>] [--installer <path>] [--skip-os-probes]` (`make compliance-evidence`), and `GET /api/compliance/report` in `desktop/compliance_routes.ts` with one dispatch line in `desktop/dev.ts`. The route is UI-token only (in neither `QUERY_TOKEN_ROUTES` nor `AGENT_ROUTES`). `desktop/audit_export.ts` exports `defaultAuditPath()` so the report reads the same path the file sink writes.
6. `.github/workflows/compliance-evidence.yml` (new; existing workflows untouched) runs on `v*` tags and on demand: CycloneDX SBOM with cdxgen 12.9.0 over the lockfiles (the repo's `harness/maintainer/sbom.ts` is manifest-level, so it cannot produce a full SBOM), gitleaks 8.30.1 with `--redact` over the full history, osv-scanner 2.7.0 over `bun.lock`, `desktop/bun.lock`, `extensions/vscode/bun.lock` and `scanner-sidecar/uv.lock`, and the evidence CLI with `--skip-os-probes`. gitleaks and osv-scanner are pinned release binaries checked against their published SHA-256 rather than `gitleaks-action` (which needs a license key for organization repos). Scanner findings do not fail the job; their exit codes are recorded beside the reports.
7. `docs/compliance/README.md` (what LUCID is, boundary diagram, CUI flows, shared responsibility, reference configuration, where-to-look index per OS), `poam.md` (12 verified gaps) and `evidence-guide.md` (per-family commands).

**Report checks and status rules.** 03.13.11 pass only when a FIPS 140-validated module performs the crypto. 03.13.08 never passes while provider TLS is Bun's (POA&M P-1); it fails when neither the vault is under OS custody nor the system disk is encrypted. 03.13.10 passes for a readable vault under DPAPI / Keychain / Secret Service. 03.01.03 passes when managed policy forces the CUI lockdown, partial when only the user turned it on. 03.04.02 passes with a managed policy, else customer. 03.13.06 fails on allow-all, passes when policy holds allow-all off. 03.03.01 fails when managed logging is disabled, partial before the first event. 03.03.08 is at best partial (no hash chain, user-deletable). 03.01.05 passes when managed policy requires or locks the sandbox. 03.17.03 follows the binary's signature. 03.01.10 and 03.05.03 are stated as customer controls.

**Consequences.** An assessor gets a complete Rev 3 map with a Rev 2 column, an honest gap list and repeatable evidence. No new EventName (the report is read-only and emits nothing). The matrix must be updated when a security feature lands; the CSV / Markdown drift test and the report-to-matrix test keep the three artifacts consistent.

**Verification.** `bun test desktop/compliance_report.test.ts` (matrix coverage 130 / 97 / 33 / 17 families, Rev 2 id format, Markdown is the CSV's rendering, every report check exists in the matrix with matching Rev 2 ids, Contract D shape, every status rule, probes against isolated seams write nothing and carry no secret, route, CLI flags). Root `bunx tsc --noEmit -p .`. `bun run tools/compliance/evidence.ts --out <dir>` on a Windows host.

**Not verified here:** macOS and Linux probe paths (`fdesetup`, `codesign`, `lsblk`, `/proc/sys/crypto/fips_enabled`); the workflow has not run on GitHub (cdxgen and osv-scanner lockfile support for `bun.lock` / `uv.lock` is from their documentation); the MSI per-machine install path is electron-builder's default, not observed.
