## ADR-0477 -- P-VAULT-ENV.1: .env import into the engine vault + workspace-scoped secrets (2026-11-03)

**Status:** Accepted -- BUILT in source and tests. Proof: `bun test desktop/env_file.test.ts desktop/vault_env_import.test.ts desktop/renderer/vault_env_view.test.ts`. Builds on ADR-0474 (P-VAULT-V2.1: Contract B `desktop/vault_store.ts`, `workspaceRef`, the `ws:<hash>:<ENV>` ref convention, `/api/vault/*` in `desktop/vault_routes.ts`) and ADR-0473 (P-FIPS.1, the crypto underneath). Reuses the per-host git token slots of P-FLEET.L2 (`git_url.ts` `gitCredRef` / `gitTokenEnvName`) and the provider key slots of `settings_store.setKey` (`key:<ENV>`).

**Context.** Most projects keep their credentials in a plaintext `.env` beside the code: easy to commit by accident, synced by OneDrive/Dropbox, readable by any process. After V2 the engine vault can hold arbitrary secrets with metadata and a workspace scope, but nothing moved a `.env` into it, and nothing handed a workspace's own secrets to the agent working in that workspace (git tokens and provider keys were global env; there was no per-workspace channel).

**Decision.**
1. **Parser (`desktop/env_file.ts`, pure).** `parseDotEnv(text)`: `NAME=value` with optional `export `, whitespace around `=`, full-line `#` comments, inline comments only after whitespace (`a#b` keeps its `#`, so passwords containing `#` survive), single quotes and backticks literal, double quotes with `\n \r \t \" \\ \$` escapes, quoted values spanning lines, CRLF and a UTF-8 BOM. Duplicates: the last assignment wins (dotenv semantics), every occurrence keeps its line span. A malformed line is reported by line number only (never its text, which may be a secret), and parsing resumes on the next line. `blankDotEnv(text, names?)` rewrites the chosen assignments (every occurrence; a multi-line value collapses to one line) to `NAME=` keeping indentation, `export `, comments, other names, BOM and line-ending style byte for byte.
2. **Mapping (`mapEnvName`).** `GITHUB_TOKEN` / `GH_TOKEN` -> `git_pat_github_com`, `GITLAB_TOKEN` -> `git_pat_gitlab_com`, `AZURE_DEVOPS_EXT_PAT` -> `git_pat_dev_azure_com` (the slots Settings > Git saves; vault_env.ts injects them as `LUCID_GIT_PAT_<HOST>`, which `hostTokenForUrl` reads first). When both GitHub names are present GITHUB_TOKEN claims the slot (the order `hostTokenForUrl` reads them) and GH_TOKEN is reported as "same slot as GITHUB_TOKEN". The primary key env of every provider Settings lists (`auth_status.ts` GATEWAY/MAJORS/OTHERS) -> `key:<ENV>`. Everything else -> `workspaceRef(realpath(workspace), NAME)`, metadata `scope.workspace` = the realpath, `envName` = NAME, kind guessed from the value shape (PEM, JWT) then the name (`_PAT`, `_KEY`, `TOKEN`, `PASSWORD`). A workspace secret may not take a name that steers the process or LUCID itself (`PATH`, `HOME`, `NODE_OPTIONS`, `LD_PRELOAD`, `LUCID_*`, `OMP_*`, `BUN_*` and similar): reported as "reserved name", never imported or injected. Empty values are not importable.
3. **Import (`desktop/vault_env_import.ts`, engine-only).** `scanEnvFile` returns per name: slot, ref, injected env name, kind, last-4 (only for values of 12+ chars, `vaultLast4`), status (`new` / `same` / `replaces`, compared engine-side) and why a row is blocked; plus whether the file is git-ignored and whether git history ever held it. Never a value. `importEnvFile` stores every chosen name in ONE `mutateVault` write under the vault lock (source `env-import`, `rotatedAt` when it replaces a different value), verifies each value from what the vault returned, then sets provider keys into `process.env` (as `setKey` does) and re-runs `applyVaultEnv()` (git host tokens). Only after a verified store do the opt-in file actions run: blank the imported names (`writeAtomic`), add `/<file>` to `.gitignore`. A refused or unverified write throws and touches neither file. Only `.env` / `.env.<suffix>` directly in the workspace can be read.
4. **Committed-file detection.** `git log --all --format=%H -n 1 -- <file>` in the workspace: any hit means the file is in history on some ref; the UI then says ROTATE, because removing the file or blanking it does not remove the old values from history. Outside a repository, or if git fails, the answer is `null` (unknown), never `false`. Ignored-ness is git's own `check-ignore` inside a repository and the `.gitignore` text outside one.
5. **Injection (`workspaceSecretEnv(cwd)`).** The env overlay for a session whose cwd is a workspace, a folder inside it, or one of its lane worktrees (`<parent>/<name>.lucid-worktrees/...`, `lane_worktree.ts`); the most specific workspace wins, and only that workspace's `ws:` entries are returned. Added at the master agent spawn (`acp_backend.ts`, under the sandbox plan's env so a plan or the git PATH overlay always wins) and at every fleet lane spawn and in-place recovery (`FleetLaneManager` deps `env(laneId, cwd)` now receives the lane cwd; `dev.ts` adds the overlay). The agent's own shell and every command it runs inherit it from the omp child; nothing is written to the engine's `process.env`, so other workspaces' sessions, scanners and plugins never see it. Same timing as the git tokens: a session started after an import has the secrets; a running one picks them up on its next restart. The terminal hub window (`hub_launch.ts`) is a TUI client of the engine, not a shell in a workspace, and gets nothing new.
6. **"Write .env temporarily" (`materializeEnvFile` / `unmaterializeEnvFile`), never the default.** For a tool that only reads the file: writes this workspace's own secrets into its placeholders (missing names appended; single-quoted, or double-quoted with escapes when needed) for 1 to 240 minutes (UI offers 5/15/60), refused unless the file is git-ignored. Re-blanked by a timer, on engine exit (best-effort `process.on("exit")`), or on request. A hard kill of the engine before either leaves the values in the (git-ignored) file; the UI text says so implicitly by naming the time limit, and "Blank now" exists.
7. **HTTP (`desktop/vault_env_routes.ts`, chained from `handleVaultRoutes` with one line).** All POST, header UI token only (`x-lucid-token`; a `?t=` query token and the agent token are refused; none is in `AGENT_ROUTES`), always on the CURRENT workspace (`currentWorkspace()`), never a path from the request: `/api/vault/env/scan` `{ file? }` -> EnvScan; `/api/vault/env/import` `{ file?, names?, blank?, gitignore? }` -> `{ imported: [{ name, ref, slot, envName }], skipped: [{ name, reason }], blanked, gitignored, committed }`; `/api/vault/env/materialize` `{ file?, minutes? }` -> `{ path, names, until }`; `/api/vault/env/unmaterialize` `{ file? }` -> `{ blanked, names }`. Responses carry names, refs, counts and last-4 only. Engine log lines name env names and counts, never values.
8. **UI.** P-VAULT-UI.1's "Credential vault" section is built in parallel, so this slice ships its own collapsible Settings card "Import from .env" (`desktop/renderer/vault_env_view.ts` markup, `vault_env_panel.ts` wiring; collapsed by default and remembered through the existing `SET_OPEN` card toggle). Scan shows one row per name with slot, last-4 and status; new/replacing rows are preselected, stored/blocked ones are not (blocked ones are disabled). "Blank the imported values" and "Add .env to .gitignore" are unchecked opt-ins; a committed file shows a rotate warning and, after import, a rotate toast. The temporary write lives in a collapsed `<details>` below the import button. One-time offer: when a workspace opens (`renderWorkspaceBar`) and its `.env` has something to import, a toast offers "Review" (opens Settings at the card with the scan shown); remembered per workspace in `localStorage` (`lucid.vaultEnvOffered`), never repeated. When P-VAULT-UI.1 lands, its section can host the same card body (`vaultEnvBodyHtml`) and the separate card can be dropped.
9. **No new EventName.**

**Consequences.** A `.env` can leave the working tree in one click without breaking the project: the agent's sessions in that workspace still get every variable, git and provider credentials go where LUCID already looks for them, and the file keeps its names as documentation. A secret imported for workspace A is invisible to sessions in workspace B. A file that was ever committed is called out for rotation instead of pretending blanking fixed it. Tools that read `.env` themselves (outside an agent session) no longer find the values unless the user opts into the timed write.

**Alternatives rejected.** Put workspace secrets in the engine's `process.env` like the git tokens: every workspace's sessions, the scanner sidecar and plugins would inherit them. Store workspace secrets as `key:<ENV>`: global, and two projects with the same `DATABASE_URL` would clobber each other. Blank the file by default, or write `.env` back by default: both change the user's tree without consent. Accept a workspace path in the routes: the renderer could then read `.env` files anywhere. Cut inline comments at any `#` (dotenv's rule): breaks passwords and colour values containing `#`. Delete the file instead of blanking: loses the documentation of which names the project needs.

**Verification.** `bun test desktop/env_file.test.ts desktop/vault_env_import.test.ts desktop/renderer/vault_env_view.test.ts`: parser edge cases (export, spacing, comments, the three quote styles and escapes, multi-line values with their spans, CRLF/BOM, duplicates, malformed lines reported by number without their text); blanking keeps names, prefixes, indentation, line endings and untouched names; mapping to git host, provider key and workspace slots, GITHUB_TOKEN outranking GH_TOKEN, reserved and empty names blocked; import lands each name in its slot with `env-import` metadata, reaches `LUCID_GIT_PAT_GITHUB_COM` and the provider key env, keeps workspace secrets out of `process.env`; workspace refs stable across re-imports and distinct across workspaces; a refused vault write leaves `.env` and `.gitignore` untouched; `.gitignore` added once; a `.env` committed then removed from the index is detected through history, a never-committed one is not, outside git it is unknown; `workspaceSecretEnv` gives a workspace, its subfolders and its lane worktrees their own secrets and no other workspace's (a name-prefix sibling folder gets none); a real child spawned through `ACPClient` with that overlay sees its workspace's secret and not another's; the timed write is refused unless git-ignored and re-blanks; every route answers names only, refuses a missing/agent/query token and a non-`.env` file. Card markup: blocked rows disabled, stored rows not preselected, follow-ups unchecked, rotate warning only for committed files, temporary write inside a collapsed block.

**PROGRESS**
- **shipped:** `.env` parser and blanker (`desktop/env_file.ts`), slot mapping to the per-host git token slots, provider key slots and `ws:` workspace refs, atomic verified import (`desktop/vault_env_import.ts`) with opt-in blanking, `.gitignore` and committed-history ROTATE warning, workspace-scoped injection into the master agent and every fleet lane spawn (`workspaceSecretEnv`), the timed "write .env temporarily" action, `/api/vault/env/scan|import|materialize|unmaterialize` (UI token only, current workspace only), the Settings "Import from .env" card and the one-time per-workspace offer.
- **stubbed:** the card is its own Settings section rather than a row inside P-VAULT-UI.1's "Credential vault" (built in parallel); a running agent session sees newly imported workspace secrets only after its next restart (same as git tokens today); a timed write is re-blanked at its timer, at graceful shutdown or at the next engine start (see Security review fixes), so after a hard kill the values sit in the git-ignored file until LUCID starts again; the renderer flow is not browser-smoked by this slice.
- **next:** fold the card body into the "Credential vault" section once P-VAULT-UI.1 merges (show `ws:` entries with their workspace name there); offer "restart the agent to apply" after an import into the current workspace; let P-SECRET-INTAKE.1's `request_secret({ workspaceScoped: true })` store through `workspaceRef` so agent-requested secrets inject the same way.

## Security review fixes

- **VAULT-ENV-MATERIALIZE-SYNCED (file side).** `materializeEnvFile` refuses when the workspace or the target file (its realpath, or the folder when absent) is in a cloud-synced folder (`synced_path.ts isSyncedPath`): the client would upload the plaintext and keep versions of it. Every write is journaled first (path, names, until; never a value) in `<LUCID_DATA_ROOT or ~/.omp>/vault-env-materialized.json`, updated on every materialize and unmaterialize. `reblankMaterializedJournal()` re-blanks what the journal still lists and is called at engine start from dev.ts (through `vault_lifecycle.ts`); `unmaterializeAll()` re-blanks everything and is called from the main-only graceful shutdown route `/api/vault/main/shutdown` before Electron kills the engine. The `process.on("exit")` hook stays as a best-effort extra only. The card now promises re-blanking at the timer, a normal quit or the next start, and says synced folders are refused. Pinned by `vault_env_import.test.ts` "refused in a folder a cloud client syncs", "journaled before the write; the next start re-blanks after a crash", "unmaterializeAll re-blanks every written file and clears the journal", "main's graceful shutdown call re-blanks before the kill" (Electron main's own `engineCredClient().shutdown()` against the route; a wrong vault token changes nothing), and `vault_env_view.test.ts` "the temporary write promises re-blanking only ...".
- **SECRET-INTAKE-ENVNAME-UNRESTRICTED (import half).** The local reserved-name regex and `providerKeyEnvs` are gone: the import and `workspaceSecretEnv` use `env_name_policy.ts` (`mayHoldWorkspaceEnv`, `providerKeyEnvs`), so proxy, base URL, endpoint, CA, `GIT_*`, `PYTHON*`, `NODE_*` and `LUCID_*` names are blocked as workspace secrets. Pinned by "reserved names (runtime, proxy, base URL, git, python, CA bundle, LUCID) are blocked".
- **VAULT-ENV-IMPORT-OVERWRITE-GLOBAL.** A row that would replace a saved provider key or git host token is never pre-ticked; the card shows a "Replace my saved ... key/token" box per such row and sends its name in `confirmReplace`, and `importEnvFile` skips any replacing global row whose name is not confirmed. A `.env` git tracks (`committed`, or not ignored inside a repository; `EnvScan.tracked`) maps its provider and git names to `ws:` overrides of the workspace (`fromRepo`), never the global slots or `process.env`, unticked, with a note explaining why. Pinned by "a row replacing a saved global key is skipped unless its name is confirmed", "a git-tracked .env maps provider and git names to ws: overrides", and the two matching `vault_env_view.test.ts` cases.
- **VAULT-ENV-SYMLINK-FOLLOW.** One reader (`readEnvFileSafe`) serves scan, import, blank, materialize and the journal re-blank: `lstat` must show a regular file (no symlink, junction, FIFO or folder), at most 256 KiB, and its realpath must sit directly in the workspace realpath. Pinned by "a .env symlink is refused, never followed" (skipped where the host refuses links) and "an oversize .env is refused before it is read".
- **VAULT-DEST-AUTOBACKUP-GAP (import notify).** The import writes through the new `vault_store.ts vaultPutMany` (one locked write, verified per value, all or nothing) which then notifies every `onVaultWrite` observer per stored entry, so destination auto-backup sees imported secrets. Pinned by "an import tells every vault write observer about each imported ref, metadata only".
