## ADR-0474 -- P-VAULT-V2.1: one engine vault (v2 metadata, safeStorage migrated in, engine-side credential env, vault API) (2026-11-03)

**Status:** Accepted -- BUILT in source and tests. Proof: `make demo-P-VAULT-V2.1` (real engine processes and the real OS backend in a scratch dir) and `bun test desktop/vault_v2.test.ts desktop/cred_migration.test.ts`. Builds on ADR-0472 (P-VAULT-KEYS.1, the engine vault) and ADR-0473 (P-FIPS.1, the crypto provider); supersedes the storage half of ADR-0106 / ADR-0107 (the Electron `safeStorage` credential vault) while keeping their renderer contract.

**Context.** After P-VAULT-KEYS.1 LUCID had two secret stores. The engine vault (`desktop/engine_vault.ts`: one random master key per vault directory held by DPAPI / Keychain / Secret Service, records sealed with AES-256-GCM) held the settings keys. Electron main's `safeStorage` vault (`desktop/cred_vault.ts`, `~/.omp/lucid-cred-vault`, or the Creator flavor's own root in its userData) held every other credential: network-whitelist credentials, Agent Builder secrets, the Figma PAT, git PATs (generic and per host), Local Provider keys, the embeddings key and the Meeting Hub bearer. Main decrypted those at engine spawn and injected them as env vars, so a headless engine (hub, fleet lane, `bun run dev.ts`) had none of them and a credential saved mid-session waited for a relaunch. `safeStorage` is Chromium os_crypt, not a FIPS 140 validated module; the user decision for the vault suite is that encryption at rest uses the OS's validated module (P-FIPS.1) with a migration that needs no re-entry and loses nothing. The engine vault records also carried no metadata, which the vault UI, the secret intake, the .env import, the destinations and the compliance evidence all need.

**Decision.**
1. **Sealed format v2 with per-entry metadata.** The envelope is unchanged (`{ v, alg: "A256GCM", kid, iv, tag, ct }`, file still `secrets.v1.json`, the `v` field is the plaintext format) with `v: 2` and plaintext `{ entries: { [ref]: VaultEntryMeta & { value } } }`. v2 records are sealed with AAD `lucid-engine-vault-v2` (v1 keeps `lucid-engine-vault-v1`), so a v2 record relabelled `v: 1` fails authentication. A v1 file is still read: its entries get synthesized metadata (kind, label and env name inferred from the ref, source `migrated-settings`, addedAt/updatedAt = upgrade time) and it is rewritten as v2 on the first write that changes something; a write that changes nothing (and an empty no-op on a fresh install) writes nothing. Every entry is built in one canonical field order, so the post-write read-back compares byte for byte. `last4` is derived from the value and only for values of 12 or more characters (PEM-aware, the ADR-0107 rule). All AES-GCM, SHA-256 and random bytes go through `harness/crypto/fips_crypto.ts` (Contract A); the bytes are identical to `node:crypto`, so no record is re-encrypted. The master-key custody (DPAPI / Keychain / libsecret) is unchanged.
2. **Every P-VAULT-KEYS.1 guarantee is kept.** Writes are deltas applied under the owner-token `secrets.lock` to a map decrypted fresh inside the lock (`mutateVault(dir, plan)` computes the delta inside the lock for writes that depend on current content; `updateVault` is the fixed-delta form); the file is written atomically, read back and verified before the lock is released; a file this account's readable key cannot open is renamed aside (`.unreadable-<ts>`), never overwritten; an unreadable master key or a FIPS refusal throws and changes nothing; nothing writes a plaintext secret on a failed write; Electron main never opens the vault (outside Bun every entry point is `unavailable`).
3. **Contract B facade, `desktop/vault_store.ts`.** Directory-free API over the vault of the current settings file (`keyVaultDir()`): `vaultList`, `vaultPut` (insert or replace; an existing ref keeps source and addedAt, a changed value stamps rotatedAt), `vaultRotate`, `vaultDelete`, `vaultGet` (engine-internal only), `vaultExportEntries` / `vaultImportEntries(…, "newer-wins")` (backup and restore), `workspaceRef` and `vaultStatus()` (custody + `cryptoInfo()` + entry count). Every write throws on failure. A write that depends on the vault's content (rotate, delete, export) refuses on an unreadable vault instead of setting it aside; only a put or a restore starts a fresh vault, the ADR-0472 "re-entering a key starts a fresh vault" rule. `engine_vault.ts` keeps its directory-level `vaultStatus(dir)`; the facade's no-argument `vaultStatus()` is the Contract B one.
4. **One store: safeStorage drains into the engine vault (`desktop/cred_engine_client.ts`, main side).** The ordering that keeps every install working:
   1. At spawn main still injects env from safeStorage exactly as before (now through the shared plan `desktop/cred_env.ts`), so the first boot after the upgrade works with every credential where it was.
   2. Once the engine answers its health check (boot, and again after an engine restart), main lists every `<ref>.bin`, decrypts it and POSTs `{ ref, value, meta }` to the main-only route `/api/vault/main/import`. The engine refuses unless the vault is `ok`, stores the entry under the SAME ref with the CredMeta fields (kind, label, createdAt -> addedAt, rotatedAt, expiresAt, rotationIntervalDays; last4 re-derived) and source `migrated-safestorage`, reads the vault back, and only then answers `verified: true`.
   3. Only after that answer, carrying a verified reply MAC (see Security review fixes), does main delete the `.bin` and its `.meta.json`, and it checks the `.bin` is gone.
   4. A run that moved something writes `migrated-<ts>.json` in the cred vault (refs only, never values).
   A crash before the delete leaves the source; the next run imports again, the engine answers `present` (same value, nothing rewritten) and the delete happens then. An entry the engine already holds with a DIFFERENT value is decided newer-wins: the legacy CredMeta date (`rotatedAt ?? createdAt`) against the entry's `updatedAt`. A newer legacy value replaces the engine value (`replaced`, the entry keeps its addedAt and source); an engine value as new or newer, or a legacy copy with no date, stays (`superseded`). Either way the engine reads the winning value back before answering, and only then is the source removed. An entry safeStorage cannot decrypt, or that the engine refuses or cannot be reached for, stays where it is and keeps being injected by main. The Creator flavor migrates its own cred root into the engine vault beside its own settings file; the two never meet.
5. **Engine-side credential env (`desktop/vault_env.ts`, `applyVaultEnv()`).** Called once in `dev.ts` right after `applyEnv()` (before any omp child spawns) and after every vault write through the routes. Same env names and semantics main had, from the one plan in `cred_env.ts`: `figma_pat` -> `LUCID_FIGMA_TOKEN`, `git_pat` -> `LUCID_GIT_PAT`, `git_pat_<host_slug>` -> `LUCID_GIT_PAT_<HOST_SLUG>`, the enabled bearer/apikey embeddings `vaultRef` -> `LUCID_EMBEDDINGS_KEY`; the Meeting Hub bearer (`meeting_hub_token`) goes into `meetings_hub.ts` module state through `setMeetingHubToken`, never into `process.env` (P-MEET.1); Local Providers are re-materialized (`materializeLocalProviders`, models.yml carries env NAMES only) and `LUCID_LP_<ID>_KEY` set, reading the engine vault first and main's still-injected value second; Creator endpoints and remote targets get `LUCID_CREATOR_TARGET_<REF>`, the names `dev.ts` already reads (main never injected these, so a Creator credential now actually reaches its endpoint). A UI write of a `key:<ENV>` ref updates `process.env[ENV]` the way `setKey` does. The module removes only names it set itself, never a name main injected; an engine-vault value for a name main also injected replaces it (after migration both are the same; after a later rotation the vault holds the newer one). Only env names are logged.
6. **Bridge `cred*` keeps its names and shapes; the store behind it is the engine vault.** `bridge.credStore`, `credStoreFile`, `credList`, `credDelete`, `credRotate`, `credRotateFile` and `credEncryptionAvailable` still go renderer -> preload -> main IPC; main's handlers now call the engine's main-only routes (`/api/vault/main/store|list|rotate|delete|status`). File uploads are still read in main, so secret bytes never cross to the renderer. `credList` returns the engine's credentials (refs in the legacy credential charset) plus any not yet migrated; `credDelete` removes from both stores; rotating a ref still in safeStorage moves it into the engine with the new value; storing a ref that still has a safeStorage copy removes that copy. There is no safeStorage or plaintext fallback: an engine refusal is an `{ error }`. `credEncryptionAvailable` answers whether the engine vault is usable.
7. **HTTP surface, `desktop/vault_routes.ts`, one dispatch line in `dev.ts`.** UI routes (Contract B): `GET /api/vault/list` -> `{ status, entries }`, `POST /api/vault/put` `{ ref?, value, kind, label, envName?, workspace? }` (ref derived when absent: `key:<ENV>`, `ws:<hash>:<ENV>` for a workspace, else `secret:<label slug>` suffixed until free), `POST /api/vault/rotate` `{ ref, value }`, `POST /api/vault/delete` `{ ref }`. Main-only routes: the six `/api/vault/main/*` above plus `import`. Responses are `{ ok: true, data }` / `{ ok: false, error }` and carry metadata only (`VaultEntryMeta`, CredMeta, counts); a value is accepted on the way in and never written to a response, a log line or an event. Auth: none of these is in `AGENT_ROUTES` or `QUERY_TOKEN_ROUTES`; the module re-checks the `x-lucid-token` header itself (a `?t=` query token is never accepted); the main-only routes additionally require a request MAC keyed by `LUCID_VAULT_MAIN_TOKEN` (the token itself is never sent; see Security review fixes), minted per launch by Electron main, passed in the engine's spawn env and deleted from `process.env` the moment the module loads, so no omp, fleet or scanner child inherits it and the renderer (which holds the UI token) never receives it, and every reply to them is MAC-signed. What that token protects is the main-to-engine channel (the migration, which deletes safeStorage sources on the engine's word, and main's file-picker credential path), not the ref namespace: the UI routes can also put, rotate and delete refs in the legacy credential charset, and the Settings vault list needs exactly that. A headless engine has no main, so those routes answer 403. An unknown `/api/vault/*` path falls through, so later slices (backup, restore, env import, destinations) can serve their own.
8. **Personal KG DEK: no migration needed.** `harness/personal/store.ts` has a keystore-custody mode, but nothing in the shipped app uses it: `desktop/personal.ts` uses passphrase custody and documents keystore custody as a seam, and `main.ts` never seals a DEK with `safeStorage`. There is no sealed DEK to move; a future keystore custody belongs in the engine vault as `kg:dek:<storeId>`.
9. **No new EventName.**

**Consequences.** One secret store, sealed by the OS's FIPS 140 module where one is usable, with metadata every later vault slice builds on. Existing installs keep working on the first boot (main's injection is unchanged until each entry is verifiably in the engine) and lose nothing if the engine is down (nothing is deleted without the engine's verified answer). Headless engines get their credentials, and a credential saved mid-session works without a relaunch. Electron main keeps decrypting safeStorage only to drain it; once a cred root is empty main injects nothing from it. A user who downgrades after the migration finds the migrated credentials absent from the older build (their values are only in the engine vault, which that build does not read for credentials).

**Alternatives rejected.** Keep safeStorage and only add metadata: not FIPS 140 validated, and the headless and mid-session gaps stay. Let main copy into the engine and delete without a read-back: a crash or a refused write would lose the credential. Re-encrypt or rename refs during the move: call sites (whitelist `vaultRef`s, provider declarations, the git and Figma flows) reference the existing names. Run the migration and main's credential calls on the UI token alone: anything holding that token (the renderer, or a peer that captured it) could then answer or drive the migration channel, whose replies decide what main deletes from safeStorage. (This is a channel boundary, not a namespace one: the UI token can already write, rotate and delete legacy refs through `/api/vault/put|rotate|delete`, by design, for the Settings vault list. Restricting the UI routes to non-legacy namespaces was considered and rejected because that list must manage every credential.)

**Verification.** `bun test desktop/vault_v2.test.ts desktop/cred_migration.test.ts desktop/engine_vault.test.ts desktop/settings_vault.test.ts desktop/cred_vault.test.ts desktop/meetings_hub.test.ts desktop/local_providers_runtime.test.ts`: v1 -> v2 upgrade keeps every value and adds metadata (and a no-op write leaves v1 bytes untouched); put/rotate/delete/import/export semantics; a failed write (no backend, unreadable master key) refuses and leaves no value on disk or in a response; an unreadable vault is never overwritten (rotate/delete/export refuse, put sets it aside byte for byte); every UI and main-only route response is free of values; the agent token, a query token and a missing vault token are refused; dev.ts lists no vault route among the agent routes; the migration imports and the engine verifies before each delete; a crash between import and delete re-runs as `present` without rewriting the vault; nothing is deleted when the engine is down, refuses, or a blob cannot be decrypted; the Creator root migrates into its own vault only; the engine resolves the same env names and values main injected (Meeting Hub bearer in module state only); bridge cred* round-trips through the routes. `make demo-P-VAULT-V2.1` repeats the route, migration and bridge checks against real engines.

**Security review fixes (pre-release review of the merged P-FIPS.1 + P-VAULT-V2.1 code).**
- **VAULT-TRANSPORT-LOCALHOST (high).** The engine binds only `127.0.0.1`, but main reached it as `localhost`, which can resolve to `[::1]` first, a separate address any local process may bind; `/api/health` echoes the engine nonce, so a squatter could pass the health check by proxying it, then receive the UI token and the credential values and answer `verified: true` so main deletes the safeStorage source. Fixes: (1) every main-to-engine fetch in `desktop/main.ts` (both health probes, the vault client, the browser command poll and post) and the window load and navigation policy use `http://127.0.0.1:${PORT}`. (2) The main-only routes authenticate both directions with the vault token, which no longer travels on the wire: main sends a fresh 32-byte nonce (`x-lucid-vault-nonce`) and `x-lucid-vault-auth = HMAC-SHA256(token, "lucid-vault-request-v1\0" || method "\0" path "\0" || nonce || SHA-256(body))`; the engine verifies it in constant time (else an unsigned 403) and signs every reply with `x-lucid-vault-mac = HMAC-SHA256(token, nonce || SHA-256(responseBody))`. `cred_engine_client.ts` checks that MAC in constant time before it trusts anything in the reply, status included; a missing or wrong MAC is a refusal (`EngineVaultError`, status 0), so the migration deletes a source only after a verified MAC on a `verified: true` reply. The layout has one definition (`vaultRequestMac` / `vaultResponseMac` in `cred_engine_client.ts`); the engine computes it with Contract A (`hmacSha256` / `sha256` from `fips_crypto.ts`), Electron main with `node:crypto`: main never has a validated module (ADR-0473), so routing this check through `fips_crypto` would refuse every bridge.cred* call on a FIPS-required host; the MAC authenticates a loopback peer and protects no data at rest. Residual: the request is not replay-protected (a replay needs a captured request, i.e. a peer on the pinned 127.0.0.1 path), `/api/health` still echoes the nonce (now harmless to the vault channel), and the per-launch tokens still travel in the engine's spawn environment (the pre-existing LUCID_MAIN_TOKEN pattern). Consequence: the window origin moves from `http://localhost:PORT` to `http://127.0.0.1:PORT`, so renderer `localStorage` preferences (theme, sidebar, trivia, dock positions) start fresh once after the upgrade.
- **VAULT-MASTER-RECREATE (medium).** Inside `secrets.lock`, `mutateVault` now mints a master key only for a directory holding no sealed data: with `secrets.v1.json` or any `secrets.v1.json.unreadable-<ts>` on disk and the key record `absent`, the write throws "master key missing for an existing vault" (and `vaultStatus` reports `unreadable` when only set-aside copies remain). The explicit reset is moving those files out of the vault directory; no UI is built for it. The libsecret backend no longer trusts `secret-tool lookup` exit 1 as absence (it is also the answer for an item in a locked collection): it runs `secret-tool search --unlock` for the same attributes, and only an empty listing is `absent`; a listed item that still does not unlock is `unreadable`. `ensureMasterKey` gained `{ mayCreate }` for this. ADR-0472's "re-entering a key starts a fresh vault" now holds only when the master key is readable (another account's key, a kid mismatch).
- **MIGRATION-SUPERSEDED-DELETE (low).** Newer-wins on a value mismatch (decision 4), outcome `replaced` added; the source is deleted only after the engine read back the winning value.
- **VAULT-LOCK-STALE-TAKEOVER (low).** A stale lock is taken over by renaming it to `secrets.lock.stale-<our token>`, re-reading the renamed file and deleting it only if it still equals the stale content we judged; otherwise it was someone's fresh lock, which is put back (a hard link, which never replaces a newer lock) and the waiter backs off.
- **VAULT-V2-MIXED-ENGINE (low).** A sealed file whose envelope `v` is above `VAULT_FORMAT_MAX` (2) raises `VaultFormatTooNewError` before any key check: it reads as `unreadable` with that reason, is never set aside, and every write refuses with a clear error. The pre-ADR-0474 line (546802a) has no such rule; it must not ship alongside a v2 vault, or it gets the same backport.
- **VAULT-MAIN-BOUNDARY-MOOT (low).** The UI routes keep rotating and removing legacy refs (the Settings vault list needs it); this ADR now states what the main-only token protects: the migration channel and main's file-picker path, not the ref namespace (decision 7, Alternatives).
- Tests: `cred_migration.test.ts` (a forged reply with no MAC, a MAC under another key, and a genuinely signed reply altered by one byte each refuse and delete nothing; newer-wins in both directions), `vault_v2.test.ts` (the raw token header no longer opens a main route; replies carry the documented MAC; a body swapped under a valid request MAC is refused; a v3 file is untouched and every write refused), `engine_vault.test.ts` (no key is minted over an existing sealed file or a set-aside copy; moving the copy out is the reset; a stale-lock takeover leaves no `.stale-` file). `make demo-P-VAULT-V2.1` adds the forged-reply check against a real engine; `demo_p_vault_keys_1.ts` now proves the refusal and the explicit reset instead of the old set-aside.

**PROGRESS**
- **shipped:** engine vault format v2 with per-entry metadata (v1 read, upgraded on the first real write) routed through the P-FIPS.1 provider; Contract B facade `desktop/vault_store.ts`; `/api/vault/list|put|rotate|delete` (UI token only) and main-only `/api/vault/main/*` behind per-launch vault-token MACs on every request and reply in `desktop/vault_routes.ts`, reached at 127.0.0.1 only; the safeStorage credential vault drained into the engine vault (import, newer-wins, engine read-back, verified reply MAC, then delete; crash-safe and idempotent; Creator root isolated); no master key minted over sealed data; newer-format files never touched; engine-side credential env (`LUCID_FIGMA_TOKEN`, `LUCID_GIT_PAT`, `LUCID_GIT_PAT_<HOST>`, `LUCID_EMBEDDINGS_KEY`, `LUCID_LP_<ID>_KEY`, `LUCID_CREATOR_TARGET_<REF>`, the Meeting Hub bearer in module state) at startup and on every change; bridge cred* unchanged for the renderer, backed by the engine vault.
- **stubbed:** no Settings UI for the vault yet (P-VAULT-UI.1 consumes `/api/vault/list` and the backup/restore exports); the Electron main side (IPC handlers, boot-time migration) is exercised through `cred_engine_client.ts` with a stand-in SafeStorageLike, not inside a running Electron window; macOS Keychain and Linux Secret Service custody paths are unchanged from ADR-0472 and not exercised on this Windows host; the personal KG keystore custody remains a documented seam (nothing to migrate).
- **next:** P-VAULT-UI.1 (inventory, rotation badges and encrypted backup/restore over this API), P-SECRET-INTAKE.1 and P-VAULT-ENV.1 (agent-triggered entry and workspace-scoped `ws:` secrets through `vaultPut`), P-VAULT-DEST.1 (push/pull to enterprise destinations), P-COMPLY.1 (report `vaultStatus()` under 03.13.11); an in-app pass that upgrades a real install with safeStorage credentials and confirms the migration marker and unchanged Figma, git, Local Provider and Meeting Hub behavior.
