## ADR-0473 -- P-FIPS.1: at-rest crypto runs in the OS's FIPS 140 module (Windows CNG / Apple corecrypto / OpenSSL FIPS provider) (2026-11-03)

**Status:** Accepted -- BUILT in source and tests. Proof: `make demo-P-FIPS.1` (real module, no mocks) and `bun test harness/crypto/fips_crypto.test.ts`. Refines ADR-0010's "the runtime is Bun/BoringSSL, so there is no FIPS mode in-process; validation is an OS/module concern": the at-rest primitives now run in the OS module itself.

**Context.** LUCID encrypts at rest with FIPS-approved algorithms (AES-256-GCM, PBKDF2-HMAC-SHA256, SHA-256, HMAC-SHA256), but through `node:crypto`, which under Bun is BoringSSL as compiled into the Bun binary: not a FIPS 140 validated module. NIST SP 800-171 r3 03.13.11 (r2 3.13.11) asks for FIPS-validated cryptography when it protects CUI. Every desktop OS LUCID ships on already has a validated module: Windows CNG (the Cryptographic Primitives Library, `bcryptprimitives.dll`, behind `bcrypt.dll`), Apple corecrypto (behind CommonCrypto), and on FIPS-configured Linux distributions the OpenSSL 3 FIPS provider. The user decision for the vault suite is that encryption at rest uses one of these where the OS provides it, with a migration that needs no re-entry and loses no data.

**Decision.**
1. **One provider module, `harness/crypto/fips_crypto.ts` (Contract A).** Exports `cryptoInfo()`, `fipsRequired()`, `FipsRequiredError`, `randomBytes`, `aesGcmEncrypt`/`aesGcmDecrypt` (32-byte key, 12-byte IV, 16-byte tag), `pbkdf2Sha256`, `sha256`, `hmacSha256`, plus `CryptoAuthError` (tag mismatch), `cryptoSelfTest()` (the KATs, for demos and the compliance report), the pure `windowsCngClaim()` and `corecryptoClaim()`, and the `_forceModuleForTest()` seam. Every at-rest caller goes through it; `harness/personal/crypto.ts` is switched in this increment, `desktop/engine_vault.ts` is switched by P-VAULT-V2.1.
2. **Per-OS module, bound through `bun:ffi`, handles cached for the process:**
   - **win32: Windows CNG.** `BCryptOpenAlgorithmProvider` for `AES` (with `BCryptSetProperty(ChainingMode = ChainingModeGCM)`), `SHA256`, and `SHA256` with `BCRYPT_ALG_HANDLE_HMAC_FLAG`; `BCryptGenerateSymmetricKey` per operation (CNG-owned key object), `BCryptEncrypt`/`BCryptDecrypt` with a `BCRYPT_AUTHENTICATED_CIPHER_MODE_INFO`, `BCryptGenRandom(NULL, ..., BCRYPT_USE_SYSTEM_PREFERRED_RNG)`, `BCryptDeriveKeyPBKDF2` on the HMAC handle, `BCryptHash` (Windows 10+) for SHA-256 and HMAC-SHA256. `STATUS_AUTH_TAG_MISMATCH` (0xC000A002) maps to `CryptoAuthError`. `osFipsPolicy` is `HKLM\System\CurrentControlSet\Control\Lsa\FipsAlgorithmPolicy\Enabled` read once through `reg query` (absent value = off, reg.exe unavailable = null).
   - **darwin: Apple corecrypto through CommonCrypto** (`/usr/lib/system/libcommonCrypto.dylib`, then `libSystem.B.dylib`): `CCRandomGenerateBytes`, `CCKeyDerivationPBKDF(kCCPBKDF2, kCCPRFHmacAlgSHA256)`, `CC_SHA256`, `CCHmac(kCCHmacAlgSHA256)`, and AES-GCM through `CCCryptorGCMOneshotEncrypt`/`CCCryptorGCMOneshotDecrypt`. Those two are SPI (CommonCryptorSPI.h), not public API: when they do not resolve the module is not used at all and the provider falls back (item 4).
   - **linux: OpenSSL 3** (`libcrypto.so.3`): used only when `EVP_default_properties_is_fips_enabled(NULL) == 1` AND `OSSL_PROVIDER_available(NULL, "fips") == 1`; then `EVP_CIPHER_fetch("AES-256-GCM")` and `EVP_MD_fetch("SHA2-256")` once, EVP AES-GCM, `PKCS5_PBKDF2_HMAC`, `EVP_Digest`, `HMAC`, `RAND_bytes`. An OpenSSL without the FIPS provider active is reported (`osFipsPolicy: false` or `true` without the provider) and not used.
3. **Power-on self-test.** Before a native module is used, it must pass known-answer tests: AES-256-GCM encrypt and decrypt of GCM test case 16 (McGrew and Viega; 60-byte plaintext, 20-byte AAD), rejection of that vector with one tag bit flipped, PBKDF2-HMAC-SHA256 (4096 iterations, 36-byte salt, 40-byte output, from OpenSSL's `evpkdf_pbkdf2.txt`), SHA-256("abc") (FIPS 180-4), HMAC-SHA256 (RFC 4231 case 2) and two distinct DRBG draws. Any failure demotes to the fallback (or, when FIPS is required, every operation refuses).
4. **Fallback `bun-boringssl` = `node:crypto`, `fips: false`.** Used when no native module binds or passes its self-test, on other platforms or architectures, and always under Electron main / Node (`typeof Bun === "undefined"`): there `bun:ffi` is never loaded; it is required lazily under an opaque specifier, as `engine_vault.ts` does for DPAPI, so a `--target=node` bundle neither resolves nor loads it.
5. **When is `fips: true`? (the claim rule).** `fips` is true only when a FIPS 140 validated OS module performs the operations AND the claim is justified for this host:
   - **Windows:** CNG passed the KATs, AND (1) the build is a Microsoft-listed validated release (`CNG_LISTED_RELEASES`, with the Cryptographic Primitives Library certificate per build), AND (2) its module runs in approved mode: either (a) the OS FIPS mode policy is on (`FipsAlgorithmPolicy\Enabled = 1`: the administrator has put Windows in its approved mode, which also enables the module self-tests on every release), or (b) the build runs the self-tests without that policy: Windows 11 22H2 (build 22621, CMVP #5410) at UBR 3447 or later (KB5036893) and Windows Server 2022 (build 20348, #5410 for 20348.1668, #4825 for 20348) at UBR 2402 or later (KB5036909). Microsoft states that since the April 2024 updates these releases run the self-tests before first use, and that "configuring the legacy FIPS policy is no longer needed". The policy puts CNG in approved mode but cannot make an unvalidated module version validated, so every other case is reported `fips: false` while CNG still performs the operations: an unknown policy, a listed Windows 10 release with the policy off (its self-tests need the policy), and any release Microsoft does not list, policy or not (Windows 10 21H2 = 19044 and 22H2 = 19045, Windows 11 23H2/24H2 and later). Enablement-package builds are deliberately NOT mapped to their base module: Microsoft Learn ("Windows FIPS 140 validation", learn.microsoft.com/windows/security/security-foundations/certification/fips-140-validation, and its "FIPS 140 validated modules for Windows 10" page, both read 2026-11-03) lists Windows 10 2004 (19041, Cryptographic Primitives Library #4536), 20H2 (19042, #4825) and 21H1 (19043, #4825) as separate validations and lists neither 21H2 nor 22H2; nothing there says those builds inherit #4536, so LUCID does not claim it. Certificates per listed build: 10240 and 10586 #2606, 14393 #2937, 15063 #3095, 16299 / 17134 / 17763 #3197, 18362 / 18363 / 19041 #4536, 19042 / 19043 / 22000 #4825, 20348 #4825 (#5410 from 20348.1668), 22621 #5410. Editions are not checked (19042/19043 list Pro and Enterprise only). The `detail` string names the build, whether Microsoft lists it, and which leg justified (or failed) the claim, so an assessor can check it against the Security Policy (CMVP #5410 is FIPS 140-3, "When operated in approved mode ... configured as specified in Section 11.1 of the Security Policy"). Exact patch-level binary matching against the certificate is the assessor's check, not something an app can prove.
   - **Linux:** the OpenSSL FIPS provider is active (default properties require `fips=yes` and the `fips` provider is loaded). Whether that provider build is the validated one is the distribution's claim (RHEL and similar ship it as a validated module); see CMVP for the module certificate of your OS build.
   - **macOS:** CommonCrypto with the GCM SPI resolved and the KATs passed, AND the Darwin release and architecture are in `CORECRYPTO_VALIDATED` (`corecryptoClaim()`): the user-space corecrypto module of that macOS release holds an ACTIVE CMVP certificate for that architecture. Table (CMVP validated-modules search, vendor Apple, status Active, each certificate's Security Policy "Tested Operational Environments", read 2026-11-03): macOS 11 Big Sur (Darwin 20) Intel #4389, Apple silicon #4391; macOS 12 Monterey (21) Intel #4951, no active Apple silicon user-space certificate; macOS 13 Ventura (22) Intel #5348, Apple silicon #5065; macOS 14 Sonoma (23) Intel #5201, Apple silicon #5216; macOS 15 Sequoia (24) Intel #5217 (module v18.3), Apple silicon #5184 (18.3). Anything else (macOS 26 before its certificate is issued, an older release) is `fips: false`: Apple submits every release, but "in process" is not "validated". corecrypto has no separate FIPS mode switch and self-tests at load, so no policy enters the rule. An x64 process under Rosetta on Apple silicon is matched as Intel, an operational environment the certificates do not list [INFERENCE: not detected]. Not exercised on a Mac in this increment.
   - **Fallback:** always `fips: false`.
6. **Fail closed when required.** `fipsRequired()` is the OR of `LUCID_FIPS_REQUIRED=1` and every managed policy source setting `security.crypto.requireFips === true`, each read on its own (`managedRequireFipsBy()` / the pure `requireFipsFrom()` in `desktop/managed_config.ts`): the GPO flat value `CryptoRequireFips` under `HKLM\Software\Policies\LucidAgentIDE`, the canonical machine policy file (`%ProgramData%\LucidAgentIDE\managed-config.json`, `/Library/Application Support/LucidAgentIDE/managed-config.json`, `/etc/lucidagentide/managed-config.json`) and the `LUCID_MANAGED_CONFIG` file; only a literal `true` counts. It is monotonic: no source can turn off what another requires (the merged config, where the first file wins and overlays the registry, is not consulted for this knob). The `FipsRequiredError` message names every requiring source. When it holds and the active module's `fips` is false, every operation (including `randomBytes(0)` and `cryptoSelfTest()`) throws `FipsRequiredError`; there is no non-validated path. `cryptoInfo()` never throws and reports `required`. The requirement is re-evaluated per call: `LUCID_FIPS_REQUIRED` as it stands, the managed sources as read once per process (like every managed knob).
7. **No migration needed.** AES-256-GCM and PBKDF2 are deterministic, so every module produces byte-identical output for the same inputs. The tests prove it against `node:crypto` for AES-256-GCM (plaintext lengths 0 to 65539 including non-multiples of 16, with no AAD, empty AAD and AAD of 1 to 71 bytes), PBKDF2 (empty to 200-byte passwords, empty to 64-byte salts, 1 to 4096 iterations, 1 to 100-byte outputs), SHA-256 (0 bytes to 1 MiB around the block boundary) and HMAC-SHA256 (empty, short, block-size and longer-than-block keys). A personal-kg.v1 blob sealed by the previous `node:crypto` code opens through the provider and vice versa, and the 600000-iteration KEK is identical. Swapping the module IS the migration; the frozen on-disk format is unchanged.

**The CNG authenticated-cipher struct.** `BCRYPT_AUTHENTICATED_CIPHER_MODE_INFO` as built (x64 and arm64 Windows share the LLP64 layout; 88 bytes, 8-byte aligned):

| offset | field | type |
| --- | --- | --- |
| 0 | cbSize (= 88) | ULONG |
| 4 | dwInfoVersion (= 1) | ULONG |
| 8 | pbNonce | PUCHAR |
| 16 | cbNonce (= 12) | ULONG |
| 20 | padding | 4 bytes |
| 24 | pbAuthData (NULL when no AAD) | PUCHAR |
| 32 | cbAuthData | ULONG |
| 36 | padding | 4 bytes |
| 40 | pbTag | PUCHAR |
| 48 | cbTag (= 16) | ULONG |
| 52 | padding | 4 bytes |
| 56 | pbMacContext (NULL, no chaining) | PUCHAR |
| 64 | cbMacContext (0) | ULONG |
| 68 | cbAAD (0) | ULONG |
| 72 | cbData (0) | ULONGLONG |
| 80 | dwFlags (0) | ULONG |
| 84 | tail padding | 4 bytes |

How it was checked: the member list and types are the Windows SDK `bcrypt.h` definition as published on Microsoft Learn (`ns-bcrypt-bcrypt_authenticated_cipher_mode_info`; no SDK is installed on the build host), and the offsets follow MSVC natural alignment on 64-bit Windows (pointers and ULONGLONG 8-byte aligned, ULONG 4, struct size rounded to 8), which matches `BCRYPT_INIT_AUTH_MODE_INFO` (zero the struct, set `cbSize = sizeof`, `dwInfoVersion = 1`). It is then proven at runtime: CNG rejects a wrong `cbSize`, and the GCM KAT and the cross-checks only produce the reference ciphertext and tag when `pbNonce`, `pbAuthData`/`cbAuthData` and `pbTag`/`cbTag` sit at exactly these offsets (the AAD-bearing vectors would fail otherwise).

Two further CNG details: a zero-length input still gets a valid one-byte buffer (CNG treats a NULL output buffer as a size query), and an empty HMAC key or PBKDF2 password is passed as the single byte 0x00, which yields the same padded key K0 (FIPS 198-1) and therefore the same output, so CNG never sees a zero-length secret.

**What is covered, and what is not.**
- Covered: the personalization store (`harness/personal/crypto.ts`, ADR-0010) now; the engine vault (`desktop/engine_vault.ts`) when P-VAULT-V2.1 switches its AES-GCM to this provider. Key custody stays with the OS (DPAPI / Keychain / Secret Service, ADR-0472); this ADR is about the cipher, KDF, hash and DRBG.
- **Residual gap: outbound TLS.** HTTPS from Bun (`fetch`) and from omp uses the BoringSSL compiled into Bun, not a validated module. Model API traffic, connectors and updates are therefore not FIPS-validated in transit. Mitigations are deployment-level (a FIPS-validated TLS-terminating egress proxy) until Bun can use the OS TLS stack; the compliance report (P-COMPLY.1) must show this as a gap, not a pass.
- **Not a validated module: Electron `safeStorage`** (`cred_vault.ts`, ADR-0106). It wraps DPAPI / Keychain / libsecret with Chromium's own AES and is used only in Electron main; P-VAULT-V2.1 migrates its entries into the engine vault and retires it.
- Electron main and plain Node always run the `node:crypto` fallback and report `fips: false`; with FIPS required they refuse.
- No CMVP certificate is asserted for Linux; see CMVP for the module certificate of your OS build. macOS and Windows claims cite the certificate in `detail`.

**Consequences.**
- No user action and no re-encryption on upgrade: existing personal stores open unchanged; new data is sealed by the OS module.
- On Windows 10 21H2/22H2 and on Windows 11 releases Microsoft does not list, LUCID reports `fips: false` whatever the FIPS policy says; with `requireFips` set, such a host refuses to encrypt until it runs a listed release (on a listed release with the policy off, enabling "System cryptography: Use FIPS compliant algorithms for encryption, hashing, and signing", or MDM `AllowFipsAlgorithmPolicy`, is enough). This is deliberate: the claim is never stronger than the evidence.
- The macOS claim table (`CORECRYPTO_VALIDATED`) must be updated when CMVP issues a certificate for a new macOS release.
- The FIPS claim table (`CNG_LISTED_RELEASES`, `CNG_AUTO_SELFTEST`) must be updated when Microsoft lists a new release.
- An FFI binding is now on the at-rest path. The KATs at first use and the fallback keep a binding failure from corrupting data; a failure demotes (or refuses), it never writes with a broken module.
- Not proven on macOS or Linux in this increment: those bindings are written to the documented (or, for the CommonCrypto GCM SPI, the published SPI header) signatures, typecheck, and fall back cleanly when a symbol is missing. [INFERENCE]

**Security review fixes (pre-release review of the merged P-FIPS.1 + P-VAULT-V2.1 code).**
- **FIPS-POLICY-LOOSENABLE (medium).** `fipsRequired()` used to read `requireFips` from the merged managed config, where the first trustworthy policy file wins (and `LUCID_MANAGED_CONFIG` is the first candidate; on Windows every file is "trustworthy") and overlays the GPO registry per leaf, so a user-chosen file saying `requireFips: false` could cancel a GPO or ProgramData mandate. It is now the monotonic OR described in decision 6: each source (env flag, GPO `CryptoRequireFips`, the canonical machine file, the `LUCID_MANAGED_CONFIG` file) is read on its own and can only add the requirement. No trust check is needed for that read: the most a forged file can do is make the host stricter. Tests: `requireFipsFrom` across every source combination, and live: a `LUCID_MANAGED_CONFIG` file alone requires FIPS; on Windows a user file saying `false` does not cancel a machine file saying `true` (the merged config still says `false`, the requirement stands); `fipsRequired()` fails closed from a policy file without the env flag and is not relaxed by a `false` file.
- **Follow-up (pre-existing, not fixed here): LUCID_MANAGED_CONFIG precedence for every other managed knob.** The merged config still takes the first trustworthy candidate, so a user-set `LUCID_MANAGED_CONFIG` displaces the canonical machine file entirely and overlays the GPO registry for every other policy (exec/egress/loop tiers and locks, models, sandbox, collab, update channel, workspace roots). Fix in its own increment: honor `LUCID_MANAGED_CONFIG` only when it is set at machine scope or the file sits in an admin-only location (Windows owner/ACL check), and never let it displace the machine file; until then, documented in the deployment runbook as an admin responsibility.
- **FIPS-CLAIM-OVERREACH (low).** Windows `fips: true` now needs a Microsoft-listed validated build AND (the FIPS policy on OR the auto-self-test patch level); the policy alone no longer claims an unlisted build (decision 5, with the sources and the explicit decision not to map 19044/19045 to the 19041 module). macOS `fips: true` now needs a Darwin release and architecture with an active CMVP certificate for the user-space corecrypto module (decision 5 table); it was unconditional. Tests: the `windowsCngClaim` table (19045 and 19044 with the policy on are not claimed, 19041 with the policy on is, certificate numbers in `basis`) and the `corecryptoClaim` table. Consequence: on this build host (Windows 10 22H2, 19045) CNG still performs every operation but reports `fips: false`, and `requireFips` refuses there.

PROGRESS
- **shipped:** `harness/crypto/fips_crypto.ts` (Contract A): Windows CNG via bun:ffi (proven byte-identical to node:crypto for AES-256-GCM with and without AAD at lengths 0 to 65539, PBKDF2, SHA-256, HMAC-SHA256; tag tampering throws), CommonCrypto and OpenSSL-FIPS bindings, power-on KATs, the documented `fips` claim rule (a Microsoft-listed Windows release AND the OS FIPS policy or its auto-self-test patch level; a macOS release and architecture with an active corecrypto CMVP certificate), fail-closed `FipsRequiredError` under `LUCID_FIPS_REQUIRED=1` or ANY managed source setting `security.crypto.requireFips` (GPO `CryptoRequireFips`, machine file, `LUCID_MANAGED_CONFIG` file; monotonic OR); `harness/personal/crypto.ts` switched with personal-kg.v1 unchanged; `make demo-P-FIPS.1`.
- **stubbed:** macOS corecrypto (GCM through SPI) and Linux OpenSSL FIPS paths are not exercised on a real host; outbound TLS (Bun/omp BoringSSL) remains a non-validated residual gap; ADMX/ADML for `CryptoRequireFips` is owed in the private add-on repo.
- **next:** P-VAULT-V2.1 moves `desktop/engine_vault.ts` sealing onto this provider and surfaces `cryptoInfo()` in `vaultStatus()`; P-COMPLY.1 reports it under 03.13.11; run the demo on a Mac and a RHEL host with the FIPS provider enabled.
