## ADR-0476 -- P-SECRET-INTAKE.1: the agent asks for a secret through a LUCID dialog, never through chat (2026-11-03)

**Status:** Accepted -- BUILT in source and unit tests. Proof: `bun test desktop/synced_path.test.ts desktop/secret_fallback.test.ts desktop/secret_intake.test.ts harness/omp/secret_intake_extension.test.ts`. Builds on ADR-0474 (P-VAULT-V2.1, the Contract B vault: `vaultPut` with source `agent-request`) and ADR-0473 (P-FIPS.1, the crypto under it). The destination half consumes Contract C from ADR-0478 (P-VAULT-DEST.1) through an injected store.

**Context.** When a task needed an API key, the agent had one way to get it: ask the user to paste it into the chat, a `.env` or a terminal. Every one of those puts the value into the model's context, the transcript, shell history or a file in the workspace, and the user decision for this suite says the agent must be able to trigger a LUCID-themed masked dialog instead, never see the value, and fall back to a plain-text file in a non-synced, user-only temp folder (Notepad on Windows) that is read on save, overwritten and deleted. The vault (ADR-0474) already stores secrets fail-closed; what was missing was the path from "the agent needs a secret" to "the user typed it into something the agent cannot read".

**Decision.**
1. **The tool: `request_secret`, an omp custom tool registered the LUCID way** (`harness/omp/secret_intake_extension.ts`, loaded with `-e` on the master spawn in `acp_backend.ts` like `browser_extension.ts`; omp is extended, not forked). Arguments: `name`, `purpose`, `kind` (a `VaultKind`), optional `envName`, optional `workspaceScoped`. `approval: "read"`: the dialog is the user's decision and the call executes nothing. Only those five fields leave the tool (`requestBody`), so a `value` the model invents, for example one copied from chat, never reaches the engine; the reply is rebuilt field by field (`formatSecretResult`) to exactly `{"stored":true,"ref":...,"envName":...}` or `{"stored":false,"reason":...}`, so even a desktop bug that put more on the wire could not hand the model anything else. Without `LUCID_SECRET_REQUEST_URL` (a plain `omp` run) the tool is not registered.
2. **Engine round trip, reusing the approval path.** The tool POSTs to `/api/secret/request` with the per-launch AGENT token (the dev.ts env-URL convention of `LUCID_SANDBOX_GRANT_URL`; the route is in `QUERY_TOKEN_ROUTES`/`AGENT_ROUTES`). `SecretIntake.open()` (`desktop/secret_intake.ts`) validates, parks the request and emits a `secret-request` ChatEvent through `backend.requestSecretDialog()`, the same active-turn stream the approval cards ride. The engine answers each poll after a 25 s hold (`{pending, id}` while the user decides), and the tool polls `{id}`; no single request outlives Bun's 60 s idle timeout or a fetch timeout. Stop on the tool sends `{id, withdraw:true}` so the dialog closes too. A request ends on the user's answer, cancel, withdraw, or a 10-minute deadline; at most 3 wait at once.
3. **Refusals before any dialog.** `parseSecretRequest` reads the five fields only, strips control/zero-width/bidi characters from what the dialog will show, refuses a missing name or purpose, an invalid `envName`, `workspaceScoped` without an `envName`, and a name or purpose that LOOKS like a secret value (the shared `scanTextsForSecrets` detectors of the Agent Builder guardrail): a key pasted into chat and copied into the request is refused, not shown and not stored.
4. **Where it lands.** The ref follows the vault's own rule (`vault_routes.derivedRef`, now exported): `key:<ENV>` for an env name, `ws:<hash>:<ENV>` when workspace-scoped (`workspaceRef` of the workspace realpath), else a free `secret:<label>` slot (re-derived at submit so nothing written meanwhile is clobbered). The dialog says when an existing entry will be replaced. `vaultPut({ source: "agent-request" })` stores it; `vault_routes.afterWrite` (now exported) refreshes the engine-side credential env exactly as a UI put does. A vault refusal leaves the request open and the dialog shows the error (fail-closed, retry or cancel); an empty capture says so and points at the text-file option.
5. **The dialog** (`desktop/renderer/secret_intake.ts`): the existing `.modal-ov`/`.modal` chrome, shield icon, who asked ("Main agent") and the agent's purpose as quoted data (textContent only), where it will be saved, a masked field (password input, or a disc-masked textarea for `pem`/`json`) with show/hide, helper text "Copy the key (Ctrl+C), click the box, then paste it (Ctrl+V)" through the platform helper (`modCombo`, so macOS shows the Cmd glyph), "Choose a key file" (Electron's native picker hands the ENGINE a path and the engine reads the file itself, `/api/secret/submit-file`, 64 KiB cap, buffer zeroed; the browser build reads it with a file input), "Use a text file instead", Cancel. The field is cleared the moment its value is read. A dialog opens only for an id THIS engine lists as pending (a collab guest's echoed event never prompts for a key), re-opens after a reload (`mountSecretIntake`), polls every 3 s and closes when the agent's request ended without the user. If building the dialog throws, the renderer starts the text-file fallback instead.
6. **The text-file fallback** (`desktop/secret_fallback.ts`). Base folder: `XDG_RUNTIME_DIR` (Linux tmpfs) or the OS temp dir (`%LOCALAPPDATA%\Temp`), never a synced folder and never the workspace; a fresh random `lucid-secret-*` directory is restricted to the current user (POSIX `0700` + `0600` file; Windows: `icacls /inheritance:r /grant:r *<user SID>:(OI)(CI)F`, SID from `whoami /user`) and VERIFIED by reading the permissions back (`stat`, or every `icacls` ACE must be the user's). Any failure removes what was created and refuses: no "best effort" plaintext file. The empty `paste-<ENV>-here.txt` opens with a fixed argv (`notepad.exe`, `open -e`, `xdg-open`; no shell). A non-empty save that is stable across two polls is read (UTF-8 or Notepad's UTF-16), the bytes are overwritten with zeros and fsynced, and the file AND its folder are deleted, so a second save from the still-open editor fails instead of recreating the secret; the dialog says all of this. Whitespace-only saves are ignored; a file over 64 KiB is wiped unread. Cancel, withdraw or the deadline wipe and delete an unread file.
7. **Synced-folder detection** (`desktop/synced_path.ts`, new: the repo had none). A path is synced when it is under a root the OS or a client announces (`%OneDrive%`, `%OneDriveCommercial%`, `%OneDriveConsumer%`, `%APPDATA%` = the roaming profile, `~/Dropbox`, `~/iCloudDrive`, `~/Library/Mobile Documents`, `~/Library/CloudStorage`, `~/Google Drive`, `~/Box`) or has a path segment named like a client folder ("OneDrive - Contoso", "Dropbox (Team)", "iCloud Drive", "Google Drive", "My Drive", "Box Sync", ...), which also catches Known Folder Move.
8. **"Do you keep another secrets manager or vault?"** After a store the dialog offers None / Azure Key Vault / AWS Secrets Manager / Google Secret Manager / HashiCorp Vault / Another one (and for Azure Key Vault the non-secret vault name, cloud and sign-in mode). The answer is always recorded as a NON-secret preference in `<LUCID_DATA_ROOT or ~/.omp>/secret-intake.json`. When `connectorStatus("kms")` says the enterprise add-on is installed AND a destination store is wired, it is also saved as a Contract C destination through that store (`DestinationStore.upsert`, ADR-0478's `upsertVaultDestination`); its refusal (incomplete config) is reported with the reason and a pointer to Settings > Vault destinations (Enterprise). Without the add-on the reply says it is an Enterprise feature. No outcome claims a destination that was not written; nothing is pushed from here; a secret-looking name or config value is refused and nothing is recorded.
9. **Teaching the agent, never in the frozen prefix (invariant 6).** The tool description carries the rule on every turn ("ALWAYS use this instead of asking the user to paste a secret into chat, a file, or a terminal"). A first-party long-form skill `.agents/skills/secret-intake/SKILL.md` (provenance in `SOURCES.md`) and a distilled built-in `INSTALLED_SKILLS` entry `secret-intake` (every flavor) carry the same rule. `harness/prompt/assembler.ts` and the `--append-system-prompt` policies are untouched.
10. **Audit, no new EventName.** Each step is a `SecurityEvent` (`category: "approval"`, `type: "secret_intake"`, `tool: "request_secret"`): prompt (asked for name/kind/ref), allow (stored as ref, via dialog/file/text-file), block (cancelled, timeout, withdrawn, vault refusal, fallback refused). Reasons carry names and refs only.
11. **HTTP surface** (`desktop/secret_routes.ts`, one dispatch line in `dev.ts`): agent token, query only: `POST /api/secret/request`. UI token, header only (a `?t=` token is refused here): `GET /api/secret/pending`, `POST /api/secret/submit`, `POST /api/secret/submit-file`, `POST /api/secret/cancel`, `POST /api/secret/fallback`, `POST /api/secret/fallback/wait`, `GET|POST /api/secret/manager`. A value is accepted on the way in and never written to a response (stored metadata is ref, kind, label, env name, last-4).

**Consequences.** The agent gets credentials without ever holding them, and the user gets one consistent, explained place to enter them, with a file-based escape hatch that does not leave the secret on a synced disk. The vault gains entries with source `agent-request` that P-VAULT-UI.1 lists like any other. Limits, stated: the tool is master-only (lanes do not load it; their event stream does not reach this dialog); a Stop that lands before the first poll returned cannot withdraw (the dialog then ends on the user's action or the deadline); the zero overwrite is best effort on copy-on-write or wear-levelled storage, and Windows 11 Notepad may keep its own tab state, so the dialog tells the user to close the tab; an `envName` secret is set in the engine at once, but a running omp child keeps the environment it was spawned with. The "another secrets manager" save needs ADR-0478's store wired into the dispatch line (below); until then the answer is recorded and the reply says so.

**Alternatives rejected.** One long HTTP request held for the whole wait: Bun's 60 s idle limit and fetch timeouts would cut it mid-decision. Reusing omp's permission prompt: it carries options, not a masked value. Letting the renderer read a picked file in Electron: the native picker returns a path, so the engine reads it and the bytes never enter the renderer. Writing the fallback file into the workspace or the user's Documents: both are routinely synced or committed. Putting the "use request_secret" rule in the frozen prefix: invariant 6.

**Verification.** `bun test desktop/synced_path.test.ts desktop/secret_fallback.test.ts desktop/secret_intake.test.ts harness/omp/secret_intake_extension.test.ts`: the tool's text is only the whitelisted fields even when the wire carries a value; extra arguments never leave the tool; the engine result, the emitted dialog view, audit lines and every HTTP response are free of the value while the vault holds it; cancel, timeout and withdraw resolve stored:false and store nothing; a chat-pasted key in the purpose is refused; a vault refusal and an empty capture keep the request open; the fallback folder is user-only with the host's REAL permissions (icacls on Windows, stat on POSIX), outside synced folders and the workspace, refuses and leaves nothing when permissions fail, and after a save the bytes are zeros before the file and folder are deleted; route tokens (agent vs UI, header vs query); the destination answer never fakes a save. The prefix-hash test (`bun run harness/scripts/demo02_prefix_hash.ts`) covers invariant 6.

**Integration note for the parent.** After ADR-0478 lands, wire its store into the one dispatch line: `destinations: { upsert: upsertVaultDestination }` (import from `./vault_destinations.ts`). The store's input `{ name, kind, config }` and `{ id, name, kind }` result already match `DestinationStore`.

**PROGRESS**
- **shipped:** `request_secret` omp tool (master spawn, whitelisted result, five-field request, poll-and-withdraw), `SecretIntake` engine flow into the Contract B vault (source `agent-request`, derived refs, fail-closed retries, audit), the LUCID masked dialog with show/hide, key-file pick, Ctrl/Cmd helper text and re-sync after reload, the notepad fallback in a verified user-only, non-synced temp folder with zero-overwrite and delete, `synced_path.ts`, the recorded "another secrets manager" answer with an honest Enterprise state, the `secret-intake` built-in and long-form skills, `/api/secret/*` routes.
- **stubbed:** saving the answer as a Contract C destination needs ADR-0478's `upsertVaultDestination` passed into the dispatch line (until then: recorded, and the reply says so); lanes do not load the tool; the dialog and Notepad flow are unit-tested in the engine and need the parent's browser and on-device smoke.
- **next:** wire the destination store at merge; on-device pass (agent asks, user pastes, cancel, key-file pick in Electron, Notepad save on Windows with the file gone afterwards); offer "Use this secret in a new session" once P-VAULT-ENV.1 injects workspace secrets into new sessions.
