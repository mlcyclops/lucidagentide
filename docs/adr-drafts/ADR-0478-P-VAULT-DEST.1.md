## ADR-0478 -- P-VAULT-DEST.1: enterprise vault destinations, core seam + Settings UI (2026-11-03)

**Status:** Accepted -- BUILT in source and tests. Proof: `make demo-P-VAULT-DEST.1` (real engine processes, the real OS vault backend and the real private add-on's kms connector, every path in a scratch dir) and `bun test desktop/vault_destinations.test.ts desktop/renderer/vault_dest_card.test.ts`. Contract C of the vault suite. Builds on ADR-0474 (P-VAULT-V2.1, the engine vault and its Contract B facade `desktop/vault_store.ts`) and ADR-0138 (the add-on seam `desktop/addon_seam.ts`). The private half is add-on ADR-A032 (kms connector verbs `put`, `list`, `pull`, `check`); the contract reserved "ADR-A015 or the next free A-number", and A015 was taken.

**Context.** After P-VAULT-V2.1 every secret the engine holds lives in one engine vault on this machine. Enterprise customers want that vault backed up to, and restorable from, their own secrets manager (Azure Key Vault first, on public and Government clouds). Cloud secrets-manager connectors are enterprise only (user decision 1; ADR-A012): the network side lives in the private add-on repo, and the public core ships the seam, the UI and an honest "not installed" state, never a fake success. The add-on side was already built (ADR-A032) with an exact request/reply contract and an exact name mapping the core has to match.

**Decision.**
1. **Destination config in settings, non-secret only.** `GuiSettings.vaultDestinations: VaultDestination[]` (`desktop/settings_store.ts`, beside the other settings types) = `{ id, name, kind: "azure-kv" | "aws-sm" | "gcp-sm" | "hashicorp-vault", config: Record<string,string>, autoBackup?, addedAt }`. `desktop/vault_destinations.ts` is the only writer: `upsertVaultDestination`, `removeVaultDestination`, `setVaultDestinationAutoBackup`, `listVaultDestinations`, all validated by `validateDestinationInput`. azure-kv accepts exactly `vaultName` (Key Vault naming rule), `cloud` (`public` | `usgov`, required, never defaulted, as the add-on requires), `auth` (`azure-cli` | `managed-identity` | `client-secret`), `tenantId?`, `clientId?`, `clientSecretRef?`; client-secret auth needs all three, and `clientSecretRef` must name an entry in the vault. Any other field is refused, so a `clientSecret` value can never be saved. Other kinds take plain-named fields; a field whose name looks like a secret (secret, password, token, apikey, credential, private key) is refused unless it is a `...Ref` that names a vault entry. At most 20 destinations.
2. **The file contract (ADR-A014 / ADR-A032), fail-closed.** Every connector call writes its request as JSON with mode 0600 into a fresh `mkdtemp` directory (`lucid-vdest-*`, chmod 0700; on Windows the per-user `%TEMP%` ACL applies), runs `bun <addon>/connectors/kms/src/cli.ts <verb> --file <req>`, and in a `finally` overwrites every file in that directory with zeros and removes the directory (retried once; a survivor is logged by path only). This holds on success, on a connector failure and on a throw. A pull's values arrive only in the request's `out` file inside the same directory, are read into memory, imported and wiped with the directory. The request `destination` is `{ kind, config }`; for client-secret auth the secret is resolved from the vault just-in-time into `config.clientSecret` and `clientSecretRef` is dropped, so the secret exists on disk only inside that 0600 file for the length of the call.
3. **Async seam with the full reply.** `addon_seam.ts` gains `runConnectorReply(name, verb, file, timeoutMs)`: the async form of `runConnector` (a push of many entries never blocks the engine's event loop), which parses the one JSON line whatever the exit code (the add-on exits 1 AND prints its line on a failure) and returns every field (`pushed`, `items`, `pulled`). `ok` is true only for exit 0 with `ok: true`. `runConnector` is unchanged for its callers.
4. **Name mapping, char for char.** `azureSecretName(ref)` = `lucid-` + the ref with every char outside `[0-9A-Za-z-]` replaced by `-`, cut to 127, nothing trimmed or collapsed; a ref with no letter or digit left is refused. Tags `lucidSecretTags(ref, kind, addedAt)` = `{ lucid-ref, lucid-kind, lucid-added }`. The test runs a table of every ref family against the literal expectations of the add-on's own test and, when the add-on is installed, against the add-on's `azureSecretName` itself. Contract C defines only this mapping; the connector answers "not implemented" for the other kinds today, so every kind uses it.
5. **Push.** `pushToDestination(id, refs?)`: every vault entry (or just `refs`) via `vaultExportEntries`, one `put` with `{ name, value, tags }` per entry, timeout 30 s + 2 s per item (max 15 min). Two refs that map to one destination name (`key:A_B`, `key:A-B`) are both refused and reported as skipped rather than one silently overwriting the other. The reply's `pushed` names are mapped back to refs.
6. **List and pull, newer-wins.** `listDestination(id)` keeps only secrets whose `lucid-ref` tag maps back to their own name (a mislabelled secret can never land under another ref; everything else is counted as `unmapped` and left alone) and marks each missing / older here / current by `updatedOn` against the local `updatedAt`. `pullFromDestination(id, refs?)` pulls the missing and older ones only, all-or-nothing (a name absent from the `out` file writes nothing), skips values identical to the local copy, and imports through `vaultImportEntries(…, "newer-wins")`: a new ref gets source `destination-pull`, kind from `lucid-kind`, `envName` for a `key:<ENV>` ref; an existing ref keeps its own metadata. After a write the engine-side credential env is refreshed (the `key:<ENV>` slot and `applyVaultEnv`), as a vault route write does. Restore never pushes back.
7. **Auto-backup on vaultPut.** `vault_store.ts` gains `onVaultWrite(fn)`: observers called after a VERIFIED `vaultPut` or `vaultRotate` with metadata only (never the value); a throwing observer never fails the write. `vaultImportEntries` (restore, pull) and the safeStorage migration do not notify: they are not new secrets. `vault_destinations.ts` subscribes at load and, when any destination has `autoBackup`, queues the ref; a burst (an `.env` import, an agent request) is coalesced 250 ms into one `put` per destination, pushes run one at a time, and the outcome (`{ at, ok, pushed, detail }`) is kept in memory per destination for the Settings view and logged with names and counts only.
8. **No value anywhere but the 0600 files.** Replies carry names, refs, versions, dates and counts. Every `detail` that leaves the module is scrubbed of every value the call involved (item values, the resolved client secret, pulled values; values under 4 chars, the add-on's same rule), as a backstop to the connector's own scrub. Validation errors name fields, never values.
9. **HTTP surface, `desktop/vault_dest_routes.ts`, chained from `vault_routes.ts` with one line.** UI header token only (re-checked here; never in `AGENT_ROUTES` or `QUERY_TOKEN_ROUTES`; a `?t=` token is refused): `GET /api/vault/destinations` (add-on status + version, kinds, destinations with their last auto-backup), `POST /api/vault/destinations/save | remove | auto-backup | check | list`, `POST /api/vault/push`, `POST /api/vault/pull`. Without the add-on every route but GET and remove answers 409 "Enterprise add-on not installed: <seam note>"; remove needs no connector. A connector outcome is a 200 with its own `ok` and value-free `detail`.
10. **Settings UI.** `desktop/renderer/vault_dest_card.ts` (pure builders) + `vault_dest_ui.ts` (hydrate + wiring), mounted from `app.ts` with one import line, one `setSkel` and one hydrate call; `bridge.vaultDest(path, body?)` is the one bridge method. Section "Vault destinations (Enterprise)", collapsed by default, its open state kept like every collapsible Settings card. Without the add-on: an honest note plus the seam's own install hint, no connector controls (a stale destination can still be removed). With it: rows with Test, Contents, Push all now (confirmed), Pull to this machine, Edit, Remove (confirmed) and an "Auto-backup new secrets" toggle; an add/edit form for Azure Key Vault whose client secret is PICKED from the vault by ref, never typed. Row labels ellipsize on one line (invariant 11); `.lp-*` row and form CSS and `.set-note` are reused, with a few `.vd-*` layout rules.
11. **No new EventName.**

**Consequences.** An enterprise user can back the LUCID vault up to Azure Key Vault (public or Government), see what is there, restore missing or newer entries, and have every new secret backed up automatically, while the core never contacts a cloud and never holds a destination secret in settings. A destination's Key Vault grows one secret per vault ref, named `lucid-<ref>`; Key Vault's own versioning and soft delete (ADR-A032) apply. Removing a destination in LUCID deletes nothing remotely. aws-sm, gcp-sm and hashicorp-vault destinations save but every connector call answers "not implemented yet" until the add-on implements them; the UI form offers azure-kv only and says so. Auto-backup outcomes are in memory (they reset on an engine restart).

**Alternatives rejected.** Load the add-on into the engine process: ADR-0138 keeps add-on code in child processes with their own dependencies. Keep values on stdout: the contract puts them only in the 0600 `out` file. Store the client secret in the destination config: settings is not a secret store; a vault ref resolves it just-in-time. Push on every vault write synchronously: a slow network would block every put; coalesced async pushes keep the write path fast. Reverse-map remote names to refs: the mapping is lossy (`key:A_B` and `key:A-B` share a name), so the `lucid-ref` tag is authoritative and must agree with the name.

**Verification.** `bun test desktop/vault_destinations.test.ts`: the name table equals the add-on's expectations (and the add-on's own function when `LUCID_ADDON_DIR` points at it); request files exist 0600 during the call and are gone after a success, a connector failure and a throw, and a pull's `out` file is gone too (no `lucid-vdest-*` dir survives any test); a push through the real seam to a fake add-on CLI (exit 0 and exit 1); a connector that echoes values in every detail is scrubbed, and no route response or log line carries a value; without the add-on the view says installed:false, writes answer 409 and auto-backup records the refusal while the connector never runs; auto-backup fires on vaultPut and vaultRotate, coalesces a burst, and ignores restore imports; colliding refs are refused; pull is newer-wins, ignores mislabelled secrets and writes nothing on a partial out file; config validation refuses secret-looking fields and dangling refs. `bun test desktop/renderer/vault_dest_card.test.ts`: collapsed by default, the not-installed state has no connector controls, escaping, the client secret picked by ref. `make demo-P-VAULT-DEST.1`: real engines, the real add-on (aws-sm, so no network), no value in any response or engine log, no request dir left in the engine's TEMP.

**PROGRESS**
- **shipped:** Contract C destinations in the core: non-secret `vaultDestinations` settings with strict validation, push / list / pull (newer-wins) / check through the add-on's kms connector over 0600 request files that are wiped after every call, `runConnectorReply` (async, full reply), the add-on's exact `azureSecretName` mapping, auto-backup on `vaultPut` / `vaultRotate` via the new `onVaultWrite` hook, value scrubbing on every detail, UI-token-only routes chained from `vault_routes.ts`, and the Settings section "Vault destinations (Enterprise)" with an honest not-installed state.
- **stubbed:** no live Azure tenant run (unit tests stub the connector; the demo uses an aws-sm destination the add-on refuses without network); aws-sm, gcp-sm and hashicorp-vault destinations are accepted but refused by the add-on until it implements them; auto-backup outcomes are in memory only; the renderer section is covered by builder tests, its in-app wiring by the parent's browser smoke.
- **next:** a live tenant pass (azure-cli and client-secret auth, public and usgov) through the Settings section; P-SECRET-INTAKE.1 records a remembered secrets manager through `upsertVaultDestination` when the add-on is installed; AWS Secrets Manager in the add-on once Contract C defines its credential config.
