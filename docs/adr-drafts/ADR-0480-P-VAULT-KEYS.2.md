## ADR-0480 -- P-VAULT-KEYS.2: omp's OAuth credentials sealed in the engine vault, served to omp by omp's own auth broker (2026-11-03)

**Status:** Accepted -- BUILT in source and tests. Proof: `make demo-P-VAULT-KEYS.2` (real engines, a real `omp acp`, the real OS vault backend, every path in a scratch home) and `bun test desktop/oauth_vault_store.test.ts desktop/oauth_migration.test.ts desktop/oauth_broker.test.ts`. Builds on ADR-0472 (P-VAULT-KEYS.1, the engine vault), ADR-0473 (P-FIPS.1, the crypto provider) and ADR-0474 (P-VAULT-V2.1, vault format v2 and Contract B). Ships behind a kill switch (decision 7).

**Context.** omp keeps every OAuth sign-in (Claude Pro/Max, ChatGPT/Codex, Copilot, Gemini, xAI, managed MCP OAuth) and every `/login` API key as a plaintext JSON row in `~/.omp/agent/agent.db` (`auth_credentials.data`: access AND refresh tokens). Refresh tokens are long-lived account keys; any process running as the user (or anything that copies the profile) reads them. After ADR-0472/0474 every other LUCID secret is sealed by the OS's FIPS 140 module; these rows were the remaining plaintext credential store. Invariant 1 forbids forking or patching omp.

The installed omp (18.8.6, the six-package pin) already ships the seam (study: BrokerShimScout). pi-ai's `AuthCredentialStore` interface (`auth/store.ts`) is what `AuthStorage` persists through; `startAuthBroker` (`auth-broker/server.ts`) wraps any `AuthStorage` in a loopback REST/SSE service; and every omp process started with `OMP_AUTH_BROKER_URL` + `OMP_AUTH_BROKER_TOKEN` opens a `RemoteAuthCredentialStore` (`auth-broker/remote-store.ts`) instead of agent.db (`auth-broker/discover.ts` `openAuthCredentialStore`), receives access tokens with the refresh token replaced by the `"__remote__"` sentinel, delegates refresh to the broker, and refuses to start when the broker is unreachable or refuses its token (issue #8096: no silent fall back to local credentials). omp's own `omp auth-broker serve` is exactly this composition over the SQLite store.

**Decision.**
1. **A vault-backed `AuthCredentialStore` that is omp's own store underneath (`desktop/oauth_vault_store.ts`).** `VaultAuthCredentialStore` delegates every operation to omp's `SqliteAuthCredentialStore` over an IN-MEMORY SQLite database, so identity keys, replacement matching, superseded-tombstone purge, CAS refresh write-back, blocks and the cache are omp's code, unchanged. The vault is the only place a credential row is persisted: each `auth_credentials` row is one Contract B entry, ref `oauth:<provider>:<identityKey>` (`oauth:<provider>:row-<id>` for identity-less rows such as `/login` API keys; a second row with the same identity, an omp tombstone, gets `:r<id>`; a segment outside the vault's ref charset, e.g. a `mcp_oauth:<url>` provider or an org-scoped `email:x|org:y` key, keeps a readable prefix plus 16 hex of its sha256), kind `oauth` or `apikey`, a label naming provider and account, source `migrated-agentdb` or `oauth-login` (two new `VaultSource` values), value = the row exactly as omp's schema holds it (sealed; its tail is the non-secret `updatedAt`, so the UI's last-4 never shows token bytes). Concerns: rows and cache (required), blocks (durable through a non-secret `oauth-blocks.json` beside the sealed file: row id, provider key, scope, until), usage ledger (host side: delegated to omp's own agent.db tables `usage_history`/`clients`/`client_usage`, which hold no secret, so the budget reader `tools/session_metrics.ts` is unchanged), refresh leases deliberately omitted (the remote-store shape the study recommends; the in-process broker is the single refresher and `AuthStorage` single-flights refreshes per row).
2. **Fail-closed writes.** Every mutation (login upsert, refresh write-back, disable, LUCID's account writes) is followed by one locked, read-back-verified vault write of the rows it changed (`mutateVault`, delta only). A write the vault refuses (no OS backend, an unreadable master key, a FIPS refusal, an unreadable file: the store checks readability first so a write never sets an unreadable vault aside) restores the in-memory table to what it held and throws `OauthVaultUnavailableError`: the login fails, the refresh fails (the old grant stays served), the account switch reports 0 changed. Nothing is ever written in plaintext and nothing is served that the vault did not take. The store refuses to open over an unusable vault.
3. **Other writers.** Before each mutation and on every broker poll (omp's `GenerationGate` calls `pollExternalChanges` every 250 ms) the store adopts changes to `oauth:` entries made by another engine on the same vault (`lucid hub`, a second app window) or by the vault UI (Remove = disconnect), keeping the ids it already serves; a ref another writer changed since the last sync is overwritten only by a row at least as new (`updated_at`), else theirs is adopted. Refs this engine never synced are never deleted; an `oauth:` entry that is not a row is skipped and left alone.
4. **omp's broker in-process (`desktop/oauth_broker.ts`, one top-level `await bootOauthVault()` in `dev.ts` right after `applyVaultEnv()`, before any omp child can spawn).** `AuthStorage(store, { refreshOAuthCredential: refreshBrokerOAuthCredential, refreshOAuthCredentialMints: true })` (the same hook omp's serve uses, imported from `@oh-my-pi/pi-coding-agent/cli/auth-broker-cli`: per-provider refresh plus the generic grant for managed MCP OAuth rows, issue #8933), then `startAuthBroker({ bind: "127.0.0.1:0", bearerTokens: [32 random bytes from the P-FIPS.1 provider, hex], refresher on })`. `OMP_AUTH_BROKER_URL`, `OMP_AUTH_BROKER_TOKEN` and `OMP_AUTH_BROKER_SNAPSHOT_TTL_MS=0` go into the engine's `process.env`, which every omp spawn inherits (`acp.ts` and `acp_backend.ts` spawn with `{ ...process.env, ...overlay }`): the master session, fleet lanes, the util connection, plugin agents. The token is per launch, never written to disk, never logged (`detail` lines name the URL only).
5. **No access token at rest on the client side.** omp's client otherwise keeps an AES-256-GCM snapshot of the ACCESS tokens in `~/.omp/cache/auth-broker-snapshot.enc`, keyed by the bearer token, for a stale-while-revalidate start. `OMP_AUTH_BROKER_SNAPSHOT_TTL_MS=0` disables both its read and its write (discover.ts). Chosen over redirecting the cache (`OMP_AUTH_BROKER_SNAPSHOT_CACHE`) because the broker is in the same engine that spawns the children, on loopback: the cache buys no availability (a child never starts without the engine), and with TTL 0 no token material is written by the client at all. The cost (a child blocks on one loopback round trip at start) is negligible.
6. **Sign-in and sign-out keep their UX.** `omp auth-broker login` always writes agent.db and `omp login` opens a browser itself (a second tab beside LUCID's own open), so neither is used on the vault path. Instead the engine runs the primitive both CLIs drive, `storage.oauth.login(provider, callbacks)`, IN-PROCESS against the broker's `AuthStorage`, behind the same shape `dev.ts` already consumes (`OauthLoginProcess`: stdout/stderr streams, a stdin that answers prompts by line, `exited`) and printing what `runTerminalOAuthLogin` prints ("Open this URL in your browser:", the instructions incl. "Enter code: ...", prompts, progress, "Login failed: ..." on stderr). The URL capture, the device-code scanner (`device_code.ts`, issue #490), pasted codes (`/api/auth/oauth-code`), Copilot's leading enterprise-domain answer, the failure note (`oauth_failure.ts`) and the respawn-on-fresh-credential check are unchanged; the credential lands sealed and the broker pushes it to running children. `dev.ts` edits: the boot line, the sign-in factory (`startOauthLoginProcess(oauthId, () => Bun.spawn([... "auth-broker", "login", oauthId]))`, the legacy spawn kept for the old path), the stdin writes, and `/api/auth/logout` skips the agent.db-only `omp auth-broker logout` spawn on the vault path (the authoritative delete follows either way). A sign-in timeout of 15 minutes bounds an abandoned flow.
7. **Kill switch and modes.** `LUCID_OAUTH_VAULT=0|off|false|no`, or managed policy `security.oauthVault: false` (new optional `ManagedSecurity.oauthVault`), keeps the old agent.db path exactly as before (mode `off`); credentials already moved stay sealed, unused, until the switch clears: they are never copied back to plaintext. Only the DEFAULT profile (engine vault `~/.omp/lucid-engine-vault`, beside the shared `~/.omp/agent/agent.db`) moves agent.db by default; any other profile (the Creator build, fleet profiles, every test and demo with its own settings file) stays `off` unless `LUCID_OAUTH_VAULT=1` opts it in, so a side profile can never carry the user's sign-ins into a vault the main app does not read. `legacy`: the vault is not usable and nothing was moved yet (agent.db untouched, old path). `refused`: the vault took the credentials before (non-secret marker `oauth-vault.json` beside the sealed file) and is not usable now: no broker, children get no stored sign-in, LUCID refuses new OAuth sign-ins rather than let them land in plaintext.
8. **Migration without a re-login (`desktop/oauth_migration.ts`).** At boot: read every `auth_credentials` row (OAuth and `/login` API keys alike: once the broker serves omp, omp never reads agent.db for credentials, so a row left behind is a lost login), merge them into the store (same tokens, same row ids where free, newer `updated_at` wins per identity, active/disabled/LUCID-parked state kept), seal (one verified vault write), read the vault back and check every source row is held, and only then delete the rows from agent.db (each only while it still holds the sealed data) with `PRAGMA secure_delete=ON`, then `wal_checkpoint(TRUNCATE)`, `VACUUM`, `wal_checkpoint(TRUNCATE)` so no freed page or WAL frame keeps a token. Any failure before the delete completes undoes the vault side and leaves agent.db untouched; on a first migration the engine then stays on the old path (`legacy`). Idempotent: a run after a crash between seal and delete finds the same data, verifies and deletes; later boots move rows a standalone omp wrote to agent.db meanwhile. The marker is written before the move and removed if a first move fails.
9. **LUCID's account features retargeted, same SQL.** `desktop/oauth_rows_target.ts` holds the live table handle; `auth_vault.ts` (re-enable after login, disconnect, sign-out-all, P-ACCT.1 park/unpark/park-all/disconnect-identity, the login fingerprint) and `auth_status.ts` (Settings status) run their existing SQL against it when it is registered (writes sealed through the store; a refused write reports the reason and changes nothing), else against agent.db (explicit `dbPath`, the kill switch, tests, tools). Parked rows drop out of the broker's snapshot exactly as omp drops them from its selection. `account_policy.ts` stays pure (comments updated). `ratelimit_probe.ts` is unchanged: it probes provider headers with LUCID's API-key slots and never read agent.db credentials. `tools/omp_auth_status.ts` and `tools/omp_auth_reenable.ts` read/repair the sealed rows offline (`openOfflineOauthRows`); a running engine adopts the repair on its next poll. The vault UI hides Rotate for `oauth:` entries (a sign-in is renewed by signing in again; a typed value would corrupt the row); Remove works as a disconnect.
10. **No new EventName.**

**Version pinning (risk).** The broker protocol is exported but NOT semver-stable (pi-ai CHANGELOG: wire schemas called internal, strict reject schemas on both sides, endpoints added with client-side 404 shims, "update the broker before clients"). The broker here is the pi-ai LUCID IMPORTS (`node_modules/@oh-my-pi/pi-ai`), the clients are whatever omp binary LUCID SPAWNS (`LUCID_OMP_BIN`, the bundled shim, a managed install). They must be the same build: the root `package.json` pins all six `@oh-my-pi/*` packages to 18.8.6 and the bundled omp shim runs that same tree; the demo asserts the spawned `omp --version` equals the imported pi-ai version. Any omp upgrade moves the pin and the bundled binary together; a user-supplied `LUCID_OMP_BIN` of a different version is unsupported on the vault path (if it misbehaves, the kill switch restores the old path). The engine logs the broker's omp version at boot (`[oauth-vault] vault: ... (omp 18.8.6)`).

**Consequences.** omp's OAuth tokens and `/login` API keys are sealed by the OS's FIPS 140 module at rest; agent.db keeps no credential row and no plaintext page; refresh tokens never leave the engine (children hold access tokens in memory only). Existing sign-ins keep working with no re-login. Every omp child now depends on the engine's broker: if it is down, omp refuses to start (by design, no plaintext fallback). The bearer token is in the engine's environment and so in every child's, including non-omp children (terminals, tools): anything that can read a child's environment can ask the loopback broker for access tokens, which is strictly less than before (it could read agent.db, refresh tokens included). An omp started OUTSIDE LUCID (plain `omp`, the `lucid` CLI launcher) reads agent.db, which no longer holds the sign-ins; its new sign-ins are moved into the vault on LUCID's next start. The Creator build shares agent.db but has its own vault and stays on the old path; on a box running both builds the main build's move takes the shared sign-ins out of Creator's reach (Creator users sign in again there, or keep the main build's switch off). A downgrade to a build before this ADR finds agent.db empty (sign in again); the sealed rows stay in the vault.

**Alternatives rejected.** A from-scratch `AuthCredentialStore`: a second implementation of omp's identity and replacement rules (org-scoped keys, tombstone purge, CAS) that drifts with every omp release; delegating to omp's own store in memory keeps them exact. Running `omp auth-broker serve` as a child: it serves agent.db, which is the problem. `omp auth-broker migrate --from-local` against LUCID's broker: it skips rows the broker already has and does not delete the source, so the verify-then-delete and the undo would still be LUCID's; one in-process path is simpler. Spawning `omp login` for sign-ins: it opens its own browser tab beside LUCID's. Redirecting the snapshot cache into a LUCID dir: still an access-token copy at rest for no availability gain. Encrypting agent.db in place (SQLCipher, a VFS): patches omp's storage layer (invariant 1). Durable refresh leases: unnecessary with one refresher per vault and CAS write-back; multi-engine races resolve newer-wins through the vault.

**Verification.** `bun test desktop/oauth_vault_store.test.ts desktop/oauth_migration.test.ts desktop/oauth_broker.test.ts` (round trip through the sealed vault and a fresh store; omp's replace/logout/tombstone semantics; refs in charset; refresh write-back through `AuthStorage` lands the new grant sealed; an unusable vault refuses to open; a refused login or refresh is rejected, not kept, and leaves no plaintext; another writer's change and removal adopted; foreign `oauth:` entries never served or deleted; migration moves every row with tokens, ids and state, agent.db + WAL keep no token bytes, idempotent, crash-between-seal-and-delete finishes without duplicates, a refusing vault and a locked agent.db each leave agent.db intact and the vault empty, newer agent.db row wins; boot puts URL/token/TTL 0 in the env and omp's own client reads access tokens with the refresh sentinel and a wrong token is refused; status, park/unpark, omp wire logout + LUCID re-enable, disconnect identity/provider, sign-out-all act on sealed rows and reach the broker's snapshot; a refused account write reports 0; the in-process sign-in prints the CLI's text, answers a pre-written prompt line, seals the credential, and a failed one exits 1 with `Login failed:`; the kill switch, a non-default profile, an unusable vault before and after a move). **PROGRESS**
- **shipped:** `VaultAuthCredentialStore` (omp's SQLite store in memory, every row sealed as `oauth:<provider>:<identityKey>`, fail-closed with rollback, multi-writer reconcile, durable blocks, usage history in omp's agent.db tables); omp's `startAuthBroker` in the engine on 127.0.0.1 with a per-launch bearer token and omp serve's refresh hook, URL + token + `OMP_AUTH_BROKER_SNAPSHOT_TTL_MS=0` in every omp spawn's env; verify-then-delete migration of agent.db (secure_delete + checkpoint + VACUUM, undo on failure, idempotent, no re-login); in-process sign-in with the CLI's exact text so redirect, device-code, pasted-code and Copilot flows keep their UX; `auth_vault.ts`, `auth_status.ts`, the omp_auth tools and the vault UI retargeted; kill switch `LUCID_OAUTH_VAULT=0` / managed `security.oauthVault=false`, default-profile ownership, `legacy`/`refused` modes; demo + 3 test files.
- **stubbed:** real provider sign-ins and real token refreshes are not exercised (no real accounts in the scratch runs: fake tokens with far expiries; the refresh path is proven with an injected refresh function and omp's own CAS write-back); the Electron window and the Settings UI are not driven (routes only); macOS Keychain / Linux Secret Service custody untested here; an omp outside LUCID (plain `omp`, the `lucid` CLI launcher) gets no broker env; the Creator build stays on agent.db.
- **next:** a live pass with real Anthropic/OpenAI/Copilot/Gemini/xAI accounts (sign-in, a forced refresh across an engine restart, park/unpark, disconnect) and a check that omp children recover after an engine restart; broker discovery for the `lucid` CLI launcher and the Creator build (a sealed endpoint record instead of env); a health watchdog that restarts the broker before respawning children; usage widgets through `GET /v1/usage`.
