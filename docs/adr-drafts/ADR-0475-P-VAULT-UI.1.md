## ADR-0475 -- P-VAULT-UI.1: vault inventory in Settings + encrypted backup/restore (2026-11-03)

**Status:** Accepted -- BUILT in source and tests. Proof: `bun test desktop/vault_backup.test.ts desktop/renderer/vault_settings_view.test.ts` (plus the unchanged `desktop/vault_v2.test.ts`). Builds on ADR-0474 (P-VAULT-V2.1: the unified engine vault, `vault_store.ts`, `/api/vault/list|put|rotate|delete`) and ADR-0473 (P-FIPS.1: every primitive through `harness/crypto/fips_crypto.ts`).

**Context.** After P-VAULT-V2.1 every secret LUCID holds (settings keys, the drained safeStorage credentials, new credentials) lives in one engine vault with per-entry metadata, but the user could not see what it holds, rotate or remove an entry from one place, or move it to a new machine. A reinstall or a new laptop meant re-entering every key. The backup must not become the weak point: it leaves the machine by design, so it must be strongly encrypted under something only the user knows, through the same validated crypto module as the vault itself, and a restore must never half-apply or silently clobber newer secrets.

**Decision.**
1. **Settings section "Credential vault"** (`desktop/renderer/vault_settings_view.ts` pure builders, `desktop/renderer/vault_settings.ts` wiring). Collapsed by default in the markup of `setCard(..., collapsible = true)` and toggled by app.ts's shared `[data-setcard]` handler, so its open state is remembered for the session exactly like every other collapsible Settings section (`SET_OPEN`); a refresh keeps the current open state. One row per vault entry from `GET /api/vault/list`: label (ref as fallback), ref, kind, where used (derived from the ref conventions: provider key `key:<ENV>`, git host `git_pat_<host>`, MCP `mcp:<id>`, workspace `ws:<hash>:<ENV>` by folder name, account, OAuth, Figma, Meeting Hub, Local Provider), last-4 (only when the engine supplies it, never for short secrets), added and updated dates, and source (typed, migrated, .env import, agent request, restore, destination pull). Rotate opens the existing popover with a masked input and calls `POST /api/vault/rotate`; Remove asks for confirmation through the sticky toast with a danger action and calls `POST /api/vault/delete`. A status note names the custody (DPAPI / Keychain / Secret Service) and the crypto module and its FIPS state; an unreadable or unavailable vault says so instead of listing. Rows follow invariant 11 (`.vault-name` owns the free space and ellipsizes, every metadata line is a nowrap block). Builders read only named metadata fields, so a stray field is never rendered.
2. **Backup format `.lucidvault`** (`desktop/vault_backup.ts`). JSON envelope `{ v: 1, kdf: { algo: "PBKDF2-HMAC-SHA256", iter: 600000, salt }, alg: "A256GCM", iv, tag, ct }` (base64; 16-byte salt, 12-byte iv, 16-byte tag). Key = PBKDF2-HMAC-SHA256(passphrase, salt, 600000, 32); `ct` = AES-256-GCM over `{ entries: vaultExportEntries(), exportedAt }` with the header `{ v, kdf, alg }` as AAD, so editing any header field (iteration count, salt, version) fails authentication. All primitives are Contract A (`pbkdf2Sha256`, `aesGcmEncrypt/Decrypt`, `randomBytes`), so the backup is made by the OS FIPS 140 module where one is usable and refused (`FipsRequiredError`) when FIPS is required and none is. Refs and labels are inside the ciphertext too. A new backup needs a passphrase of at least 10 characters (the UI asks for it twice and shows a strength hint); the derived key and plaintext buffers are zeroed after use.
3. **Restore is authenticate-then-write, newer-wins.** `openVaultBackup` parses the envelope (refusing an unknown version or algorithm, a malformed field, or an iteration count outside 100000..10000000 before any derivation), derives the key, decrypts, and checks the content; only then does `restoreVaultBackup` call `vaultImportEntries(entries, "newer-wins")`, a single locked vault write: a ref the vault lacks is added, one whose backup copy has a later `updatedAt` replaces it, anything else (equal or older) is kept. A wrong passphrase and a tampered file both fail the GCM tag and write nothing (the user sees "the passphrase is wrong or the backup file was altered"; the two are cryptographically indistinguishable). The reply is counts only: added / updated / skipped.
4. **Routes** (`desktop/vault_backup_routes.ts`, chained in `dev.ts` with one dispatch line after `handleVaultRoutes`, which answers null for these paths): `POST /api/vault/backup { passphrase }` -> `{ file, filename, count }` where `file` is the envelope JSON text (ciphertext; returning it is allowed) and `filename` is `lucid-vault-YYYYMMDD-HHMM.lucidvault`; `POST /api/vault/restore { passphrase, file }` -> `{ added, updated, skipped }`. UI token in the header only: neither path is in `AGENT_ROUTES` or `QUERY_TOKEN_ROUTES`, and the module re-checks the header token itself, so the agent token or a `?t=` query token is refused. Bodies are capped at 16 MiB. A restore that adds or updates refreshes the engine-side credential env (`key:<ENV>` refs into `process.env`, then `applyVaultEnv()`), as a V2 write does. No value and no passphrase appears in any response, log line or event.
5. **Saving the file.** Under Electron the renderer calls a new preload method `saveTextFile` (IPC `lucid:saveTextFile`): main shows the native save dialog and writes the text the renderer already holds to the chosen path with mode 0600. In a plain browser the file is a Blob download. Restore reads the chosen file with a standard file input (the Chromium picker is the OS dialog under Electron) and sends its text.
6. **No new EventName.**

**Consequences.** The vault is visible and manageable without exposing a value: the renderer only ever holds metadata, a ciphertext backup, and what the user types into masked inputs (cleared after each submit). A backup can move to any machine and restore into a vault with a different master key; restoring an old backup never rolls back a secret rotated since. The backup's strength is the passphrase's: 600000 PBKDF2 rounds slow guessing, but a weak passphrase is still weak, which the strength hint and the 10-character floor address only partly. Restoring the same file twice is a no-op (all skipped).

**Alternatives rejected.** Encrypt the backup under the vault's own master key: useless on a new machine (the key is bound to this account's OS key store). Argon2id/scrypt: not available through the FIPS module (PBKDF2-HMAC-SHA256 is the SP 800-132 approved KDF). Restore policy "backup wins": silently reverts rotations made after the backup. Return the plaintext export to the renderer and encrypt there: plaintext would leave the engine. Let the engine write the backup to a path the renderer names: an engine-side file write to an arbitrary path on a renderer request is a larger surface than main writing to a path the user just chose in a native dialog.

**Verification.** `bun test desktop/vault_backup.test.ts`: round trip into a fresh vault with a different master key keeps every value and its metadata, the envelope has the specified header and field sizes and contains no value, ref, label or passphrase in the clear, and restoring twice skips everything; a wrong (or empty) passphrase refuses with the vault file byte-for-byte unchanged; flipping a byte of ct, tag, iv or salt, or changing the iteration count, refuses as `auth`, while a bad version, algorithm, base64, truncated JSON or out-of-range iteration count refuses as `not-a-backup`, all with the vault unchanged; newer-wins: an older backup entry is skipped, a newer one replaces value and metadata, a missing one is added, an equal timestamp is skipped; a short passphrase is refused; the routes answer ciphertext and counts only (no value, no passphrase in any body), 422 on a wrong passphrase or tampered file with nothing written, 400 on a missing file or weak passphrase, refresh `process.env` for a restored `key:<ENV>`; the agent token, no token and a `?t=` query token get 403; dev.ts chains the handler and lists neither path among the agent or query-token routes. `bun test desktop/renderer/vault_settings_view.test.ts`: collapsed by default, one Rotate and one Remove per row, backup/restore forms with masked inputs, a stray `value` field never rendered, labels escaped, unreadable state and load errors shown, where-used and source labels, passphrase strength.

**PROGRESS**
- **shipped:** Settings > Credential vault (collapsed by default; per-entry label, ref, kind, where used, last-4, added/updated dates, source; masked Rotate and confirmed Remove over `/api/vault/rotate|delete`); encrypted `.lucidvault` backup (PBKDF2-HMAC-SHA256 600000 + AES-256-GCM with an authenticated header, all through the P-FIPS.1 provider) and newer-wins restore via `POST /api/vault/backup|restore` (UI header token only, ciphertext and counts only); native save dialog under Electron (`saveTextFile` preload IPC) with a browser-download fallback.
- **stubbed:** the Electron save dialog path and the in-app section are covered by unit tests of the builders and the engine routes, not by a test inside a running Electron window; macOS Keychain and Linux Secret Service custody labels are shown but not exercised on this Windows host.
- **next:** a browser/Electron smoke of the section (open, rotate, remove, back up, restore with right and wrong passphrase); P-VAULT-ENV.1 adds "Import from .env" to this section; P-VAULT-DEST.1 adds push/pull to enterprise destinations beside the local backup; rotation-due badges from `rotationIntervalDays` / `expiresAt` in the row.
