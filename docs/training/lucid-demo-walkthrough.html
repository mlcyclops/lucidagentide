TARGET FILE (one file, nothing else): demos/market-desk/index.html

WHY THIS SHAPE: the Preview panel runs pages in a sealed frame with no network

data, and then upgrade itself to live data automatically when the same file is

PHASE 1 - REAL DATA, THROUGH THE GATE (you do this yourself, first, before delegating)
Fetch current figures for: S&P 500 (^GSPC), Nasdaq Composite (^IXIC), Dow Jones
(^DJI), Russell 2000 (^RUT), VIX (^VIX), US 10-year Treasury yield, Bitcoin, gold,
WTI crude, EUR/USD. For each one get: last price, absolute change, percent change,
day range, 52-week range, and a 90-day daily close series. Also get the 10 largest
S&P 500 constituents by index weight with the same fields, and 8 market headlines
with source name, timestamp and URL.

Record the source URL and the retrieval timestamp for every single number. Write
the whole result into the file as one inline BAKED_SNAPSHOT JSON object with a
visible "as of" timestamp. If a source is blocked or unreachable, leave that series
out and say so in a data notes block inside the file. Never invent a number and
never fill a gap with a plausible-looking value.

PHASE 2 - FAN OUT (delegate these six with the task tool, one subagent each, all in
one batch so they run in parallel)

1. Ticker Rail Engineer. Sticky top rail, one tile per tracked index. Large last
   price, signed change and percent in green or red, a sparkline drawn on canvas
   from the 90-day series, and a brief pulse on update. Every tile is a button.

2. Drill-Down Analyst. A full-panel detail view per instrument. Interactive line
   and candle chart with a 1D / 5D / 1M / 6M / 1Y range switch, a crosshair readout
   that follows the pointer, 20-day and 50-day moving averages, volume bars, and
   day-range plus 52-week-range gauges. Add one plain-English "what this means"
   line that is computed from the numbers, not hardcoded text.

3. Portfolio Engineer. Add-a-holding form (symbol, shares, cost basis). Positions
   table with market value, unrealized gain and loss in dollars and percent, that
   position's contribution to today's move, a portfolio weight bar, an allocation
   donut, and a total value header with a 90-day equity curve. Persist everything
   to localStorage. Ship with 6 example holdings so the panel is never empty.

4. Market Analysis Engineer. Breadth panel (advancers versus decliners), a sector
   heat-map grid, a correlation matrix across the tracked assets, 30-day realized
   volatility, drawdown-from-high bars, and a risk-on / risk-off gauge that prints
   the inputs it used directly underneath itself.

5. Media Desk Engineer. A video panel with a dropdown of 6 finance channels:
   Bloomberg Television, Yahoo Finance, CNBC Television, Schwab Network,
   Investopedia, Nasdaq. In a real browser, embed the selected channel's live
   stream in a YouTube iframe. Inside the sealed Preview frame that iframe cannot
   load, so render a labeled placeholder card showing the channel name, the reason
   ("live video is blocked inside the sealed preview"), and a working link that
   opens the channel in a real browser. Feature-detect the environment, never
   sniff the user agent.

6. Live Data Engineer. A LIVE / SNAPSHOT toggle in the header. On load, probe
   network reachability exactly once. If reachable, poll public endpoints every 60
   seconds, patch the tiles in place without a full re-render, and show
   "LIVE - updated 12s ago" together with the source names. If not reachable, stay
   on the baked snapshot and show "SNAPSHOT - as of " with a one-line
   explanation. Every failure degrades quietly back to the snapshot, never to an
   error screen. Either way, print a data provenance table in the footer with
   source, URL and retrieved-at for every number on the page.

HOUSE RULES FOR ALL SIX
- One file. Inline CSS and JS only. No build step, no CDN, no external font, no
  remote image. Icons are inline SVG. Charts are hand-rolled canvas or inline SVG.
- Dark, dense, institutional. Deep near-black background, one restrained accent,
  green for up and red for down, tabular figures so numbers line up in columns,
  no rounded toy styling, no gradients on text.
- Never put a sentence of prose directly inside a flex container. Text lives in
  exactly one element, otherwise it shatters into narrow stacked columns.
- Every row label stays on one line and ellipsizes on overflow. No word-wrapped
  columns anywhere.
- Usable at 390px, 820px and 1440px wide.
- No em dashes anywhere in the interface or in the code.
- Define window.lucidRenderAt(tMs) so that calling it renders the exact frame for
  that timestamp with no dependence on the wall clock. All animation reads from
  that one time value. This makes the Preview panel's Capture audit deterministic.

What LUCID is doing, in plain English

You handed one paragraph to a lead. The lead read it, decided it was six separate jobs, and hired six specialists. Each specialist gets its own written brief and its own scratchpad. They work at the same time, in your actual project folder, and everything each one writes is inspected before it is allowed to land.

That is the whole idea. You are watching a small team with a supervisor and a paper trail, not an autocomplete finishing your sentences.

What LUCID is doing, in plain English

Parallel work with a paper trail. Six workers, one area of the app each, one lead merging the results. Every message and every file write is written to a log on this machine that you can read afterwards.

The workers can also message each other. When two of them want the same file, they negotiate instead of overwriting, which is why the app comes out as one coherent thing rather than six bolted-together pieces.

They will ask
Why not just have one agent do all of it?

Time and quality. Six specialists running at once finish sooner, and each one holds a smaller, sharper brief, so it does that one part better. Same reason you would not ask one person to do design, data and infrastructure at the same time.

Do they trip over each other in the same files?

Rarely, and it is handled. The lead assigns one area each, and the workers have a channel to message each other when their work overlaps. Anything one of them writes is inspected before it lands, so a collision shows up as a conversation, not as corrupted code.

Can I stop it?

Yes, instantly. There is a stop button. Better than that, you can set a hard spending cap for a run and it is enforced in the middle of a turn, so the run dies at the ceiling rather than sending you an apology afterwards.

Is our code being uploaded somewhere?

Only what the model needs to answer. The text of the request goes to the model you chose, the same as any AI tool. Everything else stays here: the logs, the memory, the credential vault, the screenshots. Those are files on this machine.

What happens if one worker produces garbage?

It gets caught at the merge. The lead reviews and integrates, and there is a separate check that stops a worker's output from being promoted into anything the system remembers long term. Bad output does not become institutional knowledge.

What LUCID is doing, in plain English

A look-and-fix loop. The agent writes the page, the panel renders it, a picture of that render goes back to the agent, and the agent corrects what it can actually see. It is the loop a designer and a developer run between them, except it takes seconds and it happens without a meeting.

The Capture button is a different thing and worth knowing about: it steps the page through a fixed sequence of moments, fingerprints each frame, and compares the result against a known-good baseline. It is a regression test for things that are visual rather than numerical.

What LUCID is doing, in plain English

Three layers, and they stack. One: everything arriving from outside is scanned for hidden or disguised instructions, including invisible characters and letters that look like other letters, before the model ever reads it. The follow-up set, this is where the quality comes from

Nobody's first build is finished. These three prompts are the whole editing workflow, and they work on any app the agent has just made. Teach the room to expect a second turn.

Polish pass
Screenshot the running app and critique it as a
senior designer who has never seen the code. Then
fix the top five problems you found. Priorities:
consistent spacing on an 8px rhythm, one type
scale, numbers in tabular figures so columns line
up, real empty states, hover and focus states on
everything clickable, and nothing clipped or
word-wrapped into a narrow column. Screenshot
again and list what changed.
Make it mine
Change it to fit how I actually work:
- I care most about [THE THING], so put that
  first and make it the biggest element.
- I never use [THE THING], remove it entirely
  rather than hiding it.
- Add [THE THING I WISH IT DID].
- Rename the labels to the words I actually use:
  [YOUR WORDS].
Keep my saved data working after the change, and
migrate it if the shape has to change.
Phone pass
Make this excellent on a phone held in one hand.
Switch the Preview panel to phone portrait, take a
screenshot, and fix what you see: tap targets at
least 44px, the primary action reachable by thumb,
tables become stacked cards, no horizontal
scrolling anywhere, text at least 16px so it does
not trigger zoom on focus. Then screenshot phone
portrait, phone landscape and desktop, and confirm
all three are correct.
Prompt 11 · connect it to real data, safely
I want this fed by my real data. Do it in the safe order:
1. First add an Import CSV button that parses a bank, broker or calendar export
   entirely inside the page, uploads nothing, and shows me what it understood
   before it commits anything.
2. Then tell me which of the numbers on this page could come from a free public
   source, name the source for each, and tell me what it would cost in rate limits.
3. Only then, if a paid key is genuinely needed, tell me exactly which key, what
   it can access, and what happens if it leaks. Put it in the credential vault,
   never in the file, and never print it into our chat.
Do not touch step 3 until I have seen steps 1 and 2.
Worth showing live if the room is asking about integration. It demonstrates the habit you want people to have: import before integrate, public before paid, vault before file.
What LUCID is doing, in plain English

Exactly what it did in the big demo. Same lead, same specialists, same inspection at the gate, same preview. The only variable is how clearly you said what you wanted.

That is why the template has a Show Me section. Most people describe features. The fastest route to software you actually open every day is to name the number you will look at first, and let the agent work backwards from that.

They will ask
Do I need to know what localStorage means?

No. It is already in the template. It means your data survives closing the window. That is the whole thing you need to know.

Can I change it after it is built?

That is the normal way to work. Describe what is wrong in plain words. The three follow-up prompts above cover most of it, and you can keep going as long as you like.

Can it connect to my bank or my brokerage?

Start with a CSV export, which is safe and takes one prompt. A live connection needs a key, and keys go into the encrypted vault behind an approval, never into the file. Prompt 11 above walks that in the right order.

Can I share it with my family or my team?

It is one file. Email it, drop it on a shared drive, or open it on your phone. Nothing to install and no account to create.

Who owns what it wrote?

You do. It is a file in your folder. LUCID is the tool that produced it, the same as a word processor and a document.

Will it still work in a year, or will it rot?

One file with no dependencies is the most durable software there is. Nothing to update, no library that goes stale, no service that shuts down. It opens in any browser.
